# EchoMind 重点代码

这份文档按一次 HTTP `/chat` 请求的实际执行顺序阅读源码。代码块只摘关键语句；省略的字段和分支以文字说明，完整实现以链接中的源文件为准。需要排查具体阈值时，先看本页对应函数，再看 [业务流程说明](业务流程说明.md) 中的完整流程。

## 1. HTTP 入口：先读记忆，再识别和编排

**源码**：[api/main.py](../api/main.py) 中的 `chat()`、`ChatResponse`。

```python
conv_id = req.conv_id or str(uuid.uuid4())
mem_ctx = await _memory.get_context(req.user_id, conv_id, query=req.message)
history = [
    {"role": m.role.value, "content": m.content}
    for m in mem_ctx.recent_messages[-5:]
] if mem_ctx.recent_messages else None

intent_result = await _orchestrator.recognize_intent(req.message, history=history)
full_context = mem_ctx.to_prompt_text()
```

这段代码说明两种“历史”的用途不同：`history` 只取最近 5 条消息，用于本次意图识别；`full_context` 由摘要、相关情景记忆、画像和最近对话组成，传给 Agent。识别结果中的 `intent`、`intent_group`、`urgency`、`entities` 和 `confidence` 一起放进 `Request`，避免 Orchestrator 再识别一次。

请求只需要 `message`，`user_id` 默认是 `anonymous`；没有 `conv_id` 时入口生成 UUID 并在响应中返回。客户端要继续同一会话，下一次必须带回该 `conv_id`。`request_id` 则由 Orchestrator 的 `Request` 生成，作用是定位**本次**工具轨迹，不能代替会话 ID。

```python
result = await _orchestrator.run(orch_req)
await _memory.add_message(req.user_id, conv_id, MsgRole.USER, req.message)
await _memory.add_message(req.user_id, conv_id, MsgRole.ASSISTANT, result.response)
asyncio.create_task(_memory.update_profile(req.user_id, conv_id))
```

Agent 回复完成后才写本轮消息。任一 `add_message()` 达到 15 条时会在 HTTP 请求内同步压缩；画像更新是后台任务。响应里的 `latency_ms` 来自 Orchestrator 的计时，**不包含入口记忆读取、意图识别及后续记忆写入和压缩**。单 Agent 路径从 `run()` 开始计时；并行路径在 `run_parallel()` 重新开始计时，连路由决策也不在该值内。因此这个字段不能直接当成 `/chat` 的端到端耗时。

这里已经没有 `_build_knowledge_context()` 或 `_should_use_knowledge()`。RAG 的触发点在 Agent 执行期间：

```python
knowledge_used="search_knowledge_base" in result.tools_used
```

这个字段只表示调用过检索工具，不能证明查到了有效片段、模型引用了片段，或执行过预先的“按意图检索”。`request_id` 随响应返回，可用于查工具轨迹。

响应中的 `agent_type` 是最终执行结果的 Agent 类型，`primary_agent` 是路由阶段选出的主类型。专业 Agent 执行失败并回退到 General 时，两者可能分别为 `general` 与 `technical`；排查这种情况不能只看其中一个字段。

## 2. 意图识别：三路并行、分组投票、同领域细化

**源码**：[core/intent_recognizer.py](../core/intent_recognizer.py) 中的 `recognize()`、`_vote()`、`_INTENT_GROUPS`。

```python
llm_task = asyncio.create_task(self._llm_recognize(message, history))
emb_task = asyncio.create_task(self._embedding_recognize(message)) if self._embedding_enabled else None
pat = self._pattern_recognize(message)
```

LLM 和 Embedding 并行；Pattern 同步。Embedding 首次请求懒加载各意图模板向量，尝试客户端的远端 `embeddings.create`，不可用时使用本地字符 1～3 gram 哈希向量。知识库则由 ChromaDB 的 Embedding 机制处理，两个向量路径不能混为一谈。

投票先保存每个具体意图分数，再把粗细意图汇总到同一领域：

```python
scores: Dict[IntentCategory, float] = {}
group_scores: Dict[IntentCategory, float] = {}
for result, w in weights:
    cat = result.get("intent", IntentCategory.OTHER)
    conf = result.get("confidence", 0.0)
    weighted_score = w * conf
    scores[cat] = scores.get(cat, 0.0) + weighted_score
    group = _INTENT_GROUPS.get(cat, cat)
    group_scores[group] = group_scores.get(group, 0.0) + weighted_score

best_group = max(group_scores, key=group_scores.get)
best_score = group_scores[best_group]
```

正常权重为 LLM `0.7`、Embedding `0.2`、Pattern `0.1`；禁用 Embedding 时 LLM `0.85`、Pattern `0.15`。比如 `technical` 与 `technical_login` 各得 `0.20`、`0.15`，账单得 `0.30`，技术组以 `0.35` 获胜，然后在技术组里选择最高分的具体意图。一般情况下，获胜组分数低于默认 `0.5` 阈值会返回 `other`；下述 Pattern 同组细化分支先执行，且要求 Pattern 自身置信度至少 `0.5`。

手算一个三路输出：LLM 判 `technical/0.8`，Embedding 判 `technical_login/0.7`，Pattern 因“退款”判 `refund/0.5`。具体分数分别是 `0.7×0.8=0.56`、`0.2×0.7=0.14`、`0.1×0.5=0.05`；技术组为 `0.70`，账单组为 `0.05`，结果是 `technical`、置信度 `0.70`，不是把账单 Pattern 当作细化结果，也不是把 `0.56` 当作最终置信度。若 LLM 与 Embedding 的技术结果都低，技术组虽比账单组高但只有 `0.35`，正常分支会返回 `other/0.35`。

Pattern 细化有明确的同组条件：

```python
if (best in _GENERIC_INTENTS and pat_intent in _SPECIFIC_INTENTS
        and _INTENT_GROUPS.get(pat_intent, pat_intent) == best_group
        and pat_conf >= 0.5 and best_score < 0.8):
    source_scores["refined_by_pattern"] = pat_conf
    return pat_intent, max(best_score, pat_conf), source_scores
```

例如 LLM 给 `billing/0.9`、Pattern 给 `technical_login/0.5`，账单组分 `0.63` 高于技术组 `0.05`，且两个组不同，最终不会误改成登录故障。LLM 失败时 `_vote()` 有单独兜底：优先采用有效 Embedding，再采用 Pattern；该分支不走正常加权合并。`source_scores` 返回三路原始置信度，不是乘权后的分数。

同组细化的作用是保留可执行的故障类型：例如 LLM 给 `technical/0.7`，消息中同时命中“无法登录”和“401”，Pattern 给 `technical_login/0.75`，两者属于技术组，技术组分是 `0.49+0.075=0.565`；`technical` 为粗意图，`0.565<0.8`，因此最终改为 `technical_login/0.75`。后续仍按技术大类路由，但细意图会写入请求角色契约、通用工具返回的 `intent` 和评测标签；它不会自动决定是否调用 RAG。

`recognize()` 用本轮消息前 200 字，以及最近 3 条历史各自的角色前 20 字、内容前 160 字生成缓存键。这些输入相同时会直接复用结果，三路识别和实体提取都跳过；差别只发生在更早历史或被截掉的文本后半段时，也可能命中同一键。缓存达到 1000 条时删除最早插入的 500 条。排查三路分数时，可看 `/chat` 的 `intent_source_scores`，但它只列各路原始置信度；要复现融合结果仍需知道每一路预测的类别，当前响应没有返回这些类别。

## 3. Orchestrator：先澄清或升级，再决定主辅 Agent

**源码**：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 中的 `run()`、`_route_decision()`、`_domain_scores()`、`_collaboration_targets()`。

```text
intent == other 且 confidence < 0.5、消息长度 > 2
  -> 直接返回澄清句，记录空工具轨迹
否则：CRITICAL 或 escalation / human_handoff
  -> EscalationAgent 确定性交接，escalated=true
否则：领域打分 -> 过滤不可用或监控降级类型 -> 选主 Agent -> 选辅助 Agent
```

领域分有明确来源：General 基础分 `0.1`，通用意图加 `0.55`；技术或账单对应意图各给该领域加 `0.75`。技术、账单关键词每个加 `0.18`、最多加 `0.45`；通用关键词每个加 `0.12`、最多加 `0.35`。错误码实体给 Technical 加 `0.2`，金额给 Billing 加 `0.15`，订单号给 General 加 `0.1`。

假设消息为“登录报错 401，而且重复扣款”，最终意图是 `technical_login`，提取到 `error_code=["401"]`：Technical 的分数是意图 `0.75` + `报错`、`401` 两次命中 `0.36` + 错误码实体 `0.20` = `1.31`；Billing 因 `扣款` 得 `0.18`；General 为 `0.10`。主 Agent 是 Technical，`routing_confidence` 截为 `1.0`。虽然 Billing `0.18` 未达到弱信号分数阈值 `0.45`，`_collaboration_targets()` 仍会因为明确的 `扣款` 关键词将它加入辅助 Agent。这个明确命中分支和“分数至少 0.45 且达到主分数 55%”的弱信号兜底分支各自独立。

主辅 Agent 通过 `asyncio.gather()` 并行执行。ResponseComposer 收到两条成功回复时再调用一次 LLM 合并、去重；若只剩一条成功回复则直接返回它；Composer 失败时按“主回复 + 补充说明”拼接。正常合成后的用户文本不显示内部 Agent 标签。EscalationAgent 当前只返回交接文字和标记，不创建真实工单。

这里有两个容易误读的分支。`other` 且低置信度、文本长度大于 2 时会直接返回固定澄清句，即使文本有技术关键词也不进入领域打分；`CRITICAL` 或明确转人工则绕过领域分，交给 EscalationAgent，它把意图、紧急度、已提取实体写进回复，不调用 LLM 或工单接口。普通 Agent 回复里出现“转人工”“人工客服”“无法处理”等词时，单 Agent 路径会把 `escalated` 置为 `true`，但同样没有真实交接动作。

并行结果的 `tools_used` 会按工具名去重，`tool_traces` 则逐条拼接；最终 `agent_types` 只列成功的 Agent，若全失败才回退为计划执行的类型列表。`supporting_agents` 保留的是路由计划，因此某个辅助 Agent 失败时它仍可能出现在该字段里。看执行成败应同时核对 `agent_types` 和最终回复。

## 4. Agent 工具循环：白名单与请求级状态

**源码**：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `BaseAgent._call_llm()`，[agents/tools.py](../agents/tools.py) 的 `AgentToolSpec` 和工具定义。

普通 Agent 的共享工具包括 `search_knowledge_base`，并叠加各自的本地工具。Technical 的 `lookup_error_code` 解释本地维护的常见错误码，不读取服务端日志；Billing 的检查工具只核对当前请求提供的字段，不会真的执行退款。EscalationAgent 的 `handle()` 是确定性实现，当前不进入普通模型工具循环。

```python
tools = self.get_tools()
tools_used: List[str] = []
tool_traces: List[Dict[str, Any]] = []
```

关键点是 `tools_used` 和 `tool_traces` 每次调用都在局部重新创建，通过 `AgentCallResult` 返回。共享的 Agent 实例不会保存这两个请求级列表，因此请求 A 调 `lookup_error_code`、请求 B 调 `search_knowledge_base` 时，两者的工具轨迹不会因实例级可变列表串在一起。`AgentStats` 仍是实例级累计统计，用于监控。

真实工具循环中，模型给出 `tool_use` 的名称、ID 和 JSON 参数；执行层先查该 Agent 的白名单，再校验必需参数和基本类型，运行同步或异步 handler，将 JSON 结果作为对应 ID 的 `tool_result` 回传模型。最多 3 轮模型/工具往返；模型异常或超过轮数时，`AgentCallError` 携带已经发生的工具记录。

轨迹中的 `success` 表示执行过程未抛错，`result_success` 取 handler 返回字典中的 `success`。handler 正常返回 `{"success": false}` 时，工具名仍可能出现在 `tools_used`。未知工具或参数校验失败会写入失败轨迹，但不会加到 `tools_used`。

以技术 Agent 的 `lookup_error_code` 为例，模型传 `{"error_code":"401"}`，handler 返回 `meaning="认证失败"`、Token/API Key、时间戳签名和登录状态三项检查建议，并明确 `server_log_checked=false`。若模型漏传必需的 `error_code`，`_validate_tool_input()` 抛“缺少必需参数”，该次轨迹是 `success=false`，模型仍会收到对应 `tool_use_id` 的错误 `tool_result`，可以在下一轮改参数。这个校验只检查 schema 中的必填字段、基础类型和多余字段，不检查 401 是否真的发生，也不执行服务端日志查询。

## 5. 请求工具轨迹：能查到什么，查不到什么

**源码**：[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `_record_tool_trace()`，[api/main.py](../api/main.py) 的两个 `/trace` 路由。

```text
/chat 返回 request_id
  -> GET /trace/tool/{request_id} 查看一次请求
  -> GET /trace/tools?limit=20 查看最近请求
```

`tool_calls` 包含调用 Agent、工具名、工具调用 ID、输入、`success`、`result_success`、耗时、`cached`、`reranked` 和错误文字。Orchestrator 用进程内 `deque` 存最近轨迹，默认最多 200 条；重启或切到另一进程后不能保证还能查到。工具结果正文和 fallback 标记没有保存在此轨迹中。

例如 `/chat` 返回 `request_id="abc"`，随后访问 `/trace/tool/abc`：找到时是 `{"request_id":"abc","found":true,"trace":{...}}`；未找到时 HTTP 仍返回正常响应，但 `found=false`、`trace={}`。`/trace/tools?limit=20` 按最近请求优先返回，单次请求即使没调用工具也会占一条记录，内部 `tool_calls=[]`。`limit` 在 Orchestrator 中至少按 1、最多按当前记录数取值；这不是按工具调用条数分页。

专业 Agent 失败后 `_execute()` 会尝试 GeneralAgent；若 General 成功，最终 `AgentResponse` 会替换专业 Agent 的失败响应，原专业 Agent 已执行的工具轨迹当前不会并入最终请求轨迹。因而轨迹能帮助定位已保留的调用，但不能被描述成“所有失败工具调用都完整持久化”。

## 6. RAG 工具链：模型决定是否调用

**源码**：[api/main.py](../api/main.py) 注册底层 `knowledge_search`；[agents/tools.py](../agents/tools.py) 的 `build_shared_rag_tools()` 封装 Agent 可见的 `search_knowledge_base`；[mcp/tool_manager.py](../mcp/tool_manager.py) 的 `search_with_rewrite()` 负责检索优化。

```text
模型没有发起 search_knowledge_base tool_use -> 本轮无 RAG；仍可能调用其他工具
模型发起 tool_use
  -> search_knowledge_base(query, top_k)
  -> rewrite_query() 尝试生成子查询，并保留原 query
  -> 每个子查询并行 call("knowledge_search", ...)
  -> ChromaDB 召回，按序列化内容哈希去重
  -> 结果多于 top_k 时尝试 LLM 重排，否则保留当前顺序
  -> 将结果作为 tool_result 交回模型
```

`MCPToolManager.call()` 的实际执行顺序是**先看 300 秒缓存，再查熔断，再校验参数，最后带超时执行 handler**。工具连续失败可触发熔断；知识库工具配置了 fallback，底层失败时可能返回 `{"fallback": true}` 的“知识库降级结果”。MCP 将 fallback 包装为 `ToolResult(success=True)`，所以 `knowledge_used=true` 或轨迹中的 `result_success=true` 不等于检索到有效知识。`search_knowledge_base` 包装结果也没有把子查询的 `cached` 标记向上传，因此请求轨迹中 `cached=false` 不证明底层没有命中缓存。

实际例子：ChromaDB 超时后，`knowledge_search` 的 fallback 返回“知识库暂时不可用”的片段，并带 `fallback=true`；`search_with_rewrite()` 会把它当成功列表收集，Agent 可见的 `search_knowledge_base` 返回 `success=true`、`results=[降级片段]`。这时 `/chat` 的 `knowledge_used=true` 仅说明工具走过，不能当作知识检索质量指标。另一个边界是 `search_with_rewrite()` 在有结果时把 `reranked` 设为 `true`，即使结果条数不超过 `top_k`、`_rerank()` 没有实际调用 LLM；该字段也不能单独证明发生了模型重排。

`POST /search` 直接执行同一套查询改写、并行召回与重排，但不经过 Agent 或意图识别，可用来单独验证检索结果。当前没有按意图禁用问候检索或强制技术问题检索的代码分支。

查询改写默认请求 3 个角度，实际召回列表还保留原 query 并去重；改写 LLM 失败时只查原 query。每个子查询至少取 5 条候选，再按结果字典的字符串形式求 MD5 去重，最后裁到 `top_k`。ChromaDB 结果给出 `title`、`content`、`score=1-distance`、`chunk`；此处 `score` 是向量距离变换值，不是经过人工标定的答案可信度。

## 7. 知识库：`upsert` 解决重复导入冲突

**源码**：[mcp/knowledge_base.py](../mcp/knowledge_base.py) 的 `add_documents()`，[api/main.py](../api/main.py) 的 `/knowledge/add`、`/knowledge/upload`。

```python
doc_id = hashlib.md5(f"{title}_{i}_{chunk[:50]}".encode()).hexdigest()
ids.append(doc_id)
docs.append(chunk)
metas.append({"title": title, "chunk_index": i, "total_chunks": len(chunks)})

if ids:
    self._collection.upsert(ids=ids, documents=docs, metadatas=metas)
```

同一标题、同一分片重复导入，ID 相同，`upsert` 更新该 ID 而不会因重复 ID 报错。`added_chunks` 记录本次写入片段数，不是数据库净新增数。若改动让片段前 50 字变化，ID 会变化，旧片段不会自动删除；若只改后半段而 ID 不变，则更新现有片段。导入后当前代码没有主动清空 MCP 的 300 秒检索缓存，刚导入的内容可能需要等同参数缓存过期后才反映在相同查询结果里。

例如 `/knowledge/add` 传一篇标题为“登录说明”、正文不足 500 字的文档，首次响应可能是 `added_chunks=1,total_chunks=N+1`；原样重传仍会返回 `added_chunks=1`，但总数保持 `N+1`。把正文开头 50 字改掉再传，会生成新 ID，总数可能变成 `N+2`。所以当前实现解决的是“重复 ID 报错”，并没有实现按标题替换旧版本或清理失效分片。

知识库 collection 是 `knowledge_base`；会话摘要和画像分别在 `episodic`、`user_profile`。ChromaDB 在写入和查询时处理向量，意图识别的本地字符向量不用于知识库。文件上传限制 10 MB，`.json` 解析为文档数组，其他后缀当前按 UTF-8 文本导入。

## 8. 记忆：第 15 条消息触发同步压缩

**源码**：[memory/conversation_memory.py](../memory/conversation_memory.py) 的 `get_context()`、`add_message()`、`_compress()`、`update_profile()`。

```python
await self._redis.lpush(key, json.dumps({...}))
await self._redis.expire(key, 86400)
if await self._redis.llen(key) >= self.COMPRESS_AT:
    await self._compress(user_id, conv_id)
```

上面是按源码顺序压缩后的片段，`{...}` 代表消息序列化字段。`COMPRESS_AT=15` 指消息条数，不是 15 轮；`/chat` 每轮写用户和助手两条。从空会话开始，第 8 轮写用户消息时达到 15 条：先压缩前 10 条、保留最近 5 条，再写本轮助手消息，列表变成 6 条。压缩时 LLM 总结旧消息，和原 Redis 摘要合并；ChromaDB `episodic` 存的是摘要，旧消息全文只截前 500 字放进 metadata 的 `full_text` 字段。摘要生成失败时写占位摘要，情景记忆写入失败时只记录日志。

下次请求 `get_context()` 读取当前工作记忆、按消息语义检索同会话及同用户历史、读取用户画像和当前摘要。`MemoryContext.to_prompt_text()` 最多放入 3 条相关历史及 8 条最近消息；意图识别历史单独取最近 5 条。`update_profile()` 在 `/chat` 写完两条消息后以后台任务运行，不阻塞 HTTP 响应；CLI 当前不启动这个画像任务。

情景记忆检索先用 `user_id + conv_id` 过滤；同会话结果少于 `HISTORY_TOP_K` 时，再按 `user_id` 查跨会话历史，去重后截到上限。画像更新取当前工作记忆最近 10 条，让 LLM 生成 `preferences` 和 `entities`，按用户固定 ID 写入 `user_profile`；这是每次 `/chat` 都启动的后台任务，接口响应返回时画像可能还没写完。对下一轮是否能读取到新画像，不能仅凭上一轮 HTTP 已返回来判断。

## 9. Skills：选定 Agent 后动态匹配

**源码**：[core/skill_loader.py](../core/skill_loader.py) 的 `Skill.matches()`、`SkillManager.prompt_for()`；[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `_build_system_prompt()`。

```python
skill_prompt = self._skill_manager.prompt_for(req.message, self.agent_type.value)
if not skill_prompt:
    return base_prompt
return f"{base_prompt}\n\n[动态 Skills]\n{skill_prompt}"
```

Skill 必须启用，并匹配当前 Agent 类型；有关键词时还要在当前消息中命中。比如“登录一直报 401”走 TechnicalAgent，会命中技术 Skill 的 `agents: technical` 和关键词 `401`；账单 Skill 因 Agent 类型不符不会注入。若同一句形成 Billing 辅助 Agent，它会独立匹配自己的 Skill。`POST /skills/reload` 重新扫描文件并刷新 Agent 引用，不改变已完成的响应，也不自动执行任何业务操作。EscalationAgent 当前不调用普通 `_build_system_prompt()`，因此不会动态注入 Skill。

匹配依据是本轮 `message` 的不区分大小写子串，不看历史里的关键词；`agents` 为空表示所有 Agent 可用，`keywords` 为空表示无需关键词。单个 Skill 的正文最多取 3200 字符，所有命中 Skill 的拼接总量默认最多 5000 字符，超限直接截断。`GET /skills` 可看加载到的文件、关键词和解析错误；若编辑了文件但没有调用 `/skills/reload`，运行中的 Agent 仍使用旧版内容。

## 10. Monitor：单实例也能发生类型级回退

**源码**：[monitor/performance_monitor.py](../monitor/performance_monitor.py) 的 `_routing_penalty()`，[agents/agent_orchestrator.py](../agents/agent_orchestrator.py) 的 `_monitor_degraded()`。

```python
if success_rate < 0.90:
    penalty += min(0.5, (0.90 - success_rate) * 2)
if avg_ms > 3000:
    penalty += min(0.4, (avg_ms - 3000) / 10000)
return min(penalty, 0.9)
```

Monitor 默认每 10 秒采样并回写惩罚值。同类多实例时，`routing_score()` 用成功率、延迟和 `monitor_penalty` 选相对健康的实例。当前每类只有一个实例，因此 Orchestrator 还检查：Technical 或 Billing 的**全部**实例惩罚值是否达到 `ECHOMIND_MONITOR_FALLBACK_PENALTY`（默认 `0.5`）；达到时将该专业类型从本次可选领域中剔除，`routing_reason` 追加 `monitor_fallback=[...]`。

例如成功率 `0.60`、平均耗时 `4000 ms`，惩罚是 `0.5 + 0.1 = 0.6`，超过默认回退阈值。下一次 Monitor 完成采样后，单实例 Technical 请求会改选其他可用领域；成功率 `0.85`、耗时 `4000 ms` 得 `0.1 + 0.1 = 0.2`，虽可能触发告警，却不发生类型级回退。General 和 Escalation 不参与这项过滤。

新实例尚无请求时 `success_rate=1.0`、`avg_ms=0`，计算惩罚为零；降权依赖已有调用统计和下一次采样，不会在单次失败后同步更新。若 Technical 被剔除而 Billing 仍可用，路由会重新在剩余分数里选最高分，可能是 Billing，也可能是 General，不能笼统说一定回退 General。`routing_score()` 只负责同类型多实例择优；类型级过滤才让单实例部署的 Monitor 降权真正改变主路由。

## 11. 评测：内部指标与 API 输出要区分

**源码**：[evaluation/evaluator.py](../evaluation/evaluator.py) 的 `IntentEvaluator.evaluate()`、`EndToEndEvaluator.run()` 和 `LLMJudge.judge()`。

意图评测比较最终细意图与预期标签，内部计算 Accuracy、Macro-F1 和每类 Precision/Recall/F1；当前 `/eval/run` API 输出 Accuracy、Macro-F1 与逐条用例 metadata，**没有直接返回 `per_class`**。对话评测直接调用 Orchestrator 生成回复，LLM Judge 分别给相关性、准确性、完整性、有用性 0～1 分，均值达到 `0.75` 才通过。Judge 调用失败时四项都设为 `0.5` 并写入 `judge_failed=true`，这代表评分失败，不能解释成回答质量恰好中等。

回归检测把本次平均指标与上一次或配置了路径的持久化 baseline 比较；相对下降超过 5% 才列为 regression。当前 API 初始化 `EndToEndEvaluator` 时没有传 `baseline_path`，所以默认只在同一进程内与上一次报告比较，重启后没有持久化基线。评测对话自行维护历史，不经过 `/chat` 的 Redis/ChromaDB 记忆读取、压缩或画像更新，因而不能把评测结果当作完整在线会话的端到端表现。

`/eval/run` 没传用例时使用内置意图和对话用例；传入 `intent_cases=[]` 或 `dialog_cases=[]` 可以让对应部分不运行。意图用例整体只生成一条 `intent_recognition` 结果，其 `passed` 由 Accuracy 是否达到 `0.75` 决定；每轮对话各生成一条结果，其 `passed` 由四项均值是否达到 `0.75` 决定。因此 `pass_rate=passed/total` 的分母是“1 条意图汇总 + 对话轮数”，不是意图样本数加对话轮数。比如 20 条意图样本汇总通过、3 轮对话中 2 轮通过，报告是 `3/4=0.75`。

回归公式是 `(当前均值-基线均值)/基线均值`，仅当基线值大于零才比较。基线 `0.80`、当前 `0.75`，相对下降 `6.25%`，会列出 regression；基线 `0.80`、当前 `0.77` 则不会。`judge_failed=true` 的对话仍按四个 `0.5` 参与均值和通过率，查看质量下降时需先排除评判模型调用失败。
