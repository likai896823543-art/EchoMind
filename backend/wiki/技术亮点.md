# EchoMind 技术亮点

本文档用于说明项目中**已实现、可定位到代码、可通过接口验证**的设计。运行效果取决于模型、Redis 和 ChromaDB 的实际状态；文中的例子用于解释分支，不代表每次模型输出都相同。业务操作边界也要说清：当前工具没有真实查单、退款或创建工单接口。

## 1. 总览：一次 `/chat` 请求怎样流转

```text
POST /chat
  -> MemoryManager.get_context() 读取最近消息、摘要、相关历史、用户画像
  -> IntentRecognizer.recognize() 并行获取 LLM / Embedding，执行 Pattern
  -> _vote() 先合并同领域粗细意图分数，再确定最终 intent 和 intent_group
  -> AgentOrchestrator.run()
       ├─ 低置信度 other 且消息长度 > 2：返回澄清问题
       ├─ CRITICAL / 转人工意图：EscalationAgent 交接回复
       └─ 其余：领域打分 -> 主 Agent + 可选辅助 Agent
             -> 单 Agent 执行，或并行执行后由 ResponseComposer 合成
             -> 模型可直接回复，也可调用白名单工具，包括 search_knowledge_base
  -> 记录 request_id 对应的工具调用轨迹
  -> 写入用户消息与最终回复，达到 15 条消息时压缩
  -> 启动异步用户画像更新，返回 ChatResponse
```

`/chat` 没有按意图预先检索知识库。RAG 由普通 Agent 的模型在执行过程中通过工具调用触发。CLI 另建 Orchestrator 和记忆管理器，未注册共享 RAG 工具，也未启动 Monitor 与画像更新，因此验证完整链路应使用 HTTP 接口。

| 亮点 | 主要代码 | 可以验证的结果 |
| --- | --- | --- |
| 三路意图融合与同组投票 | `core/intent_recognizer.py` | `intent`、`intent_group`、`intent_source_scores` |
| 主辅 Agent 路由与结果合成 | `agents/agent_orchestrator.py` | `primary_agent`、`supporting_agents`、`routing_reason` |
| 角色工具白名单与请求级轨迹 | `agents/tools.py`、`agents/agent_orchestrator.py` | `tools_used`、`/trace/tool/{request_id}` |
| 工具驱动 RAG | `agents/tools.py`、`mcp/tool_manager.py`、`mcp/knowledge_base.py` | 模型调用工具时的检索结果、`knowledge_used` |
| Redis + ChromaDB 记忆 | `memory/conversation_memory.py` | 会话上下文、压缩摘要、情景记忆、画像 |
| 动态 Skills | `core/skill_loader.py` | `/skills`、`/skills/reload` |
| 监控反馈路由 | `monitor/performance_monitor.py`、`agents/agent_orchestrator.py` | `/monitor`、`monitor_penalty`、`monitor_fallback` |
| 端到端评测 | `evaluation/evaluator.py` | `/eval/run` 的准确率、Judge 评分和回归项 |

## 2. 三路意图识别：先选领域，再选具体意图

**代码**：`core/intent_recognizer.py` 中的 `recognize()`、`_embedding_recognize()`、`_pattern_recognize()`、`_vote()`。

LLM 读取消息和最近历史，输出一个意图、置信度及 reasoning；Embedding 把消息与各意图模板做余弦相似度；Pattern 先匹配细意图关键词，未命中时再匹配粗意图关键词。LLM 与 Embedding 并行，Pattern 同步执行。当前 Embedding 实现先尝试客户端的 `embeddings.create`；该资源不可用或调用失败时使用本地字符 1～3 gram 哈希向量。这里的意图模板向量与 ChromaDB 知识库向量是两套机制。

正常投票权重是 LLM `0.7`、Embedding `0.2`、Pattern `0.1`；禁用 Embedding 时使用 LLM `0.85`、Pattern `0.15`。融合分两步：

```text
每一路意图的加权分
  -> 按 intent_group 合并：technical + technical_login + technical_crash
  -> 选择总分最高的领域
  -> 在该领域内选择得分最高的具体意图
  -> 若符合条件，允许 Pattern 在同一领域内把粗意图细化
  -> 最终置信度低于默认阈值 0.5 时返回 other
```

一个可复算的例子：把阈值设为 `0.2`，LLM 给 `billing/0.30`，Embedding 给 `technical_login/0.90`，Pattern 给 `technical/0.40`，则加权分分别为 `0.21`、`0.18`、`0.04`。虽然账单单项分高于两个技术单项，技术组总分 `0.22` 高于账单组 `0.21`，最终可选 `technical_login`。默认阈值 `0.5` 下，这组弱证据仍会返回 `other`。这个例子区分了“哪个领域获胜”和“证据是否足够”两件事。

Pattern 细化要求：当前组内获胜的是粗意图、Pattern 给出置信度至少 `0.5` 的细意图、两者属于**同一 `intent_group`**，且获胜组分数低于 `0.8`。因此 `billing` 不会被 Pattern 跨领域改成 `technical_login`。LLM 调用失败走单独兜底分支，优先采用有效 Embedding，再采用 Pattern，不执行正常加权投票。

把“跨领域误修正”代入代码更直观：LLM 给 `billing/0.90`，Embedding 给 `other/0`，Pattern 给 `technical_login/0.50`。账单组分是 `0.7 × 0.90 = 0.63`，技术组分是 `0.1 × 0.50 = 0.05`；获胜组是账单。旧条件只检查“获胜意图是否粗意图、Pattern 是否细意图”，会把结果改成 `technical_login`。现在还检查 Pattern 的组是否等于获胜组，因此最终是 `billing/0.63`。同组场景如 LLM `technical/0.80`、Pattern `technical_login/0.50`，技术组分 `0.61`，满足细化条件时返回 `technical_login/0.61`。

注意两类低置信度处理并不相同：`_vote()` 的获胜组未达到阈值时先输出 `other`；`AgentOrchestrator._needs_clarification()` 还要求消息长度大于 2、`intent_confidence < 0.5`，才直接返回澄清句。极短消息即使是 `other` 也继续走普通路由。Pattern 同组细化分支会先于普通阈值判断，返回置信度取组分数与 Pattern 原始置信度的较大值。

细意图的作用有三处：意图评测能精确区分 `technical_login` 与 `technical_crash`；路由时它给对应领域加分；Agent 的角色输入包会携带具体意图供生成回复参考。它**不单独决定** RAG 是否调用。低置信度 `other` 且用户消息去空格后长度大于 2 时，Orchestrator 会先要求澄清，不调用 Agent。

实体由规则提取 `order_id`、`date`、`amount`、`error_code`；`product` 当前是空列表。紧急度按关键词及意图判定，`CRITICAL` 会强制路由 EscalationAgent，`HIGH` 不会仅凭级别强制升级。

## 3. 主辅 Agent 编排：领域得分与协作边界

**代码**：`agents/agent_orchestrator.py` 中的 `_route_decision()`、`_domain_scores()`、`_collaboration_targets()`、`run_parallel()`、`ResponseComposer`。

当前有 General、Technical、Billing、Escalation 四类 Agent，每类默认一个实例。普通请求先给三个业务领域打分：General 基础分 `0.1`；通用、技术或账单对应意图分别加 `0.55`、`0.75`、`0.75`；领域关键词和订单号、金额、错误码实体继续加分。最高分且可用的领域成为 `primary_agent`。`routing_confidence` 是主领域分数截到 `1.0`，与意图融合的 `intent_confidence` 不同。

对“登录报错 401，而且重复扣款”这类复合消息，意图识别通常只给一个最终意图；编排器还会独立检测技术和账单关键词。命中的另一个可用专业领域可加入 `supporting_agents`。若没有明确复合信号，另一个专业领域分数至少 `0.45` 且达到主分数 `55%`，才作为弱信号兜底加入。General 不做辅助 Agent。

假设该消息的最终意图为 `technical_login`，实体提取出 `error_code=["401"]`，没有金额和订单号。`_domain_scores()` 的可复算过程是：Technical 意图加 `0.75`，`报错` 与 `401` 两个关键词加 `0.36`，错误码实体再加 `0.20`，得到 `1.31`；Billing 因 `扣款` 加 `0.18`；General 只有基础分 `0.10`。主 Agent 因此是 Technical，`routing_confidence` 截断为 `1.0`。Billing 的 `0.18` 虽达不到弱信号阈值 `0.45`，但 `_collaboration_targets()` 明确命中 `扣款`，仍可作为辅助 Agent。这说明“明确复合信号”和“弱实体分数兜底”是两条路径。

路由在打分后会过滤无实例或被 Monitor 判定降级的专业类型。若 Billing 被过滤，上例只由 Technical 处理，`routing_reason` 追加 `monitor_fallback=[billing]`。若 Technical 执行阶段报错，`_execute()` 会尝试 General；此时结果中的 `primary_agent` 仍可记录原路由决策，而 `agent_type` 是实际返回内容的 Agent，排查时应同时看这两个字段。

并行调用通过 `asyncio.gather()` 执行。ResponseComposer 只处理成功且非空的专业回复：一条成功结果直接返回；多条则再次调用 LLM 去重、整理冲突、生成一条面向用户的回复；Composer 失败时用“主回复 + 补充说明”拼接。`agent_types`、`primary_agent`、`supporting_agents` 和 `routing_reason` 保留了路由决策及执行信息，正常用户回复不显示 Agent 内部标签。

`AgentProfile` 为不同角色配置职责、工作步骤、输入输出契约、工具范围、温度和 token 上限。Technical 的输入包额外带错误码与排障字段，Billing 关注订单号、金额、支付渠道等字段。EscalationAgent 是确定性交接节点：遇到 CRITICAL 或转人工意图时返回升级原因、安全提示并设置 `escalated=true`；当前不创建工单或真正接入人工队列。

## 4. 工具调用：白名单、并发隔离和可追踪性

**代码**：`agents/tools.py` 中的 `AgentToolSpec`，`agents/agent_orchestrator.py` 中的 `BaseAgent._call_llm()`、`AgentCallResult`、`AgentCallError` 和轨迹接口。

每个普通 Agent 都向模型提供共享的 `search_knowledge_base`，再叠加角色专属工具。General 可查看当前请求上下文、建议补充字段；Technical 可查本地错误码说明、构造诊断计划；Billing 可检查账单字段、比较金额。这些工具主要处理**当前请求中已提供的信息**，不能假称已查到真实订单、执行退款或修改账号。EscalationAgent 虽有工具定义，但当前确定性 `handle()` 不进入模型工具循环。

模型返回 `tool_use` 时，执行层按白名单查找工具、校验必需参数和基本类型、调用同步或异步 handler，再把 `tool_result` 交回模型。最多执行 3 轮模型/工具往返。未知工具或参数错误会形成失败的工具结果与轨迹；超过轮数或模型异常会让该 Agent 返回失败。

**并发隔离的关键改动**是 `tools_used` 和 `tool_traces` 在 `_call_llm()` 内作为请求局部变量创建，通过 `AgentCallResult` 返回，不写入共享 Agent 实例。这样同一个 Agent 实例同时处理多个 `/chat` 请求时，工具名和轨迹不会因实例级可变列表互相串入。`AgentCallError` 在失败时携带已发生的工具记录，供失败响应使用。

实际往返可以拆成四步：第一次模型响应包含 `tool_use(id="toolu_1", name="lookup_error_code", input={"error_code":"401"})`；执行层用当前 TechnicalAgent 的白名单验证工具名和 `error_code` 参数；handler 返回本地 401 排查方向，执行层把它序列化为与 `toolu_1` 对应的 `tool_result`；第二次模型响应才是面向用户的文字。轨迹记录的是这次执行的**元数据**，并不会把排查方向全文写进 `/trace/tool/{request_id}`。

同一实例同时处理请求 A 和 B 时，A 的 `tools_used`、`tool_traces` 在 A 的 `_call_llm()` 栈内，B 另建自己的列表；它们各自随 `AgentCallResult` 进入各自的 `AgentResponse`。统计对象 `AgentStats` 仍属于共享 Agent，用于累计调用次数和耗时；并发隔离主要针对逐请求工具状态，不代表所有共享对象都变成不可变对象。

轨迹里的 `success` 表示工具调用过程没有被白名单、参数校验或异常中断；`result_success` 取工具返回字典中的 `success`，两者可能不同。`tools_used` 在 handler 正常返回后加入工具名，即使 handler 返回 `{"success": false}` 也会出现该工具名。未知工具或参数校验失败会留下失败轨迹，但不加入 `tools_used`。这些字段能回答“模型调用了什么、执行层有没有报错”，不能单独回答“检索结果是否真实有效”。

Orchestrator 为每次请求生成 `request_id`，在进程内 `deque` 保存最近轨迹，默认上限 200 条。`GET /trace/tool/{request_id}` 查单次，`GET /trace/tools?limit=20` 查最近记录。轨迹包含工具名、调用 Agent、输入、调用 ID、耗时、执行状态和错误；它不保存工具结果全文。轨迹是**进程内临时数据**，重启后消失，多进程间不共享。专业 Agent 执行失败后 `_execute()` 若用 GeneralAgent 兜底，最终响应会替换原失败响应；原专业 Agent 的工具轨迹目前不会并入本次最终轨迹，应结合日志和 Agent 统计排查。

## 5. RAG：由 Agent 工具调用触发

**代码**：`api/main.py` 注册 `knowledge_search`，`agents/tools.py` 包装 `search_knowledge_base`，`mcp/tool_manager.py` 实现检索优化，`mcp/knowledge_base.py` 执行 ChromaDB 查询。

```text
普通 Agent 把 search_knowledge_base 工具 schema 提供给模型
  ├─ 模型直接回复：不检索知识库
  └─ 模型发起 tool_use：调用 search_knowledge_base(query, top_k)
       -> LLM 尝试改写 query，保留原始 query
       -> 多个子查询并行调用 knowledge_search
       -> ChromaDB 召回片段；按内容哈希去重
       -> 多于 top_k 时尝试 LLM 重排，失败则保留原顺序
       -> 把 Top-K 结果作为 tool_result 交回模型
```

MCP 工具层有参数校验、超时、300 秒 TTL 缓存、熔断和 fallback。`POST /search` 可独立测试同一条查询改写与检索链路，不经过意图识别和 Agent。`/chat` 响应的 `knowledge_used` 只检查 `tools_used` 中是否有 `search_knowledge_base`，因此它表示“调用过检索工具”，不保证检索到了有效知识或最终回答引用了检索内容。

`search_with_rewrite()` 的具体顺序是：要求 LLM 生成 3 个角度的子查询并保留原查询；改写失败时只查原查询。每个子查询的召回数至少是 `max(top_k, 5)`，并行调用 `knowledge_search`。工具层先查缓存，再看熔断状态，随后校验参数并执行带超时的 ChromaDB handler。合并结果按序列化内容的 MD5 去重；若合并列表为空，返回 `success=false`。列表超过 `top_k` 才需要 LLM 排序，排序调用失败时截取原顺序前 `top_k`。代码在成功完成搜索链路时将 `reranked` 标为 `true`；这个布尔值不证明 LLM 确实改变了排序或改善了质量。

Agent 侧的 `search_knowledge_base` 包装结果目前只返回 `success`、`query`、`top_k`、`results` 和 `reranked`，没有把 MCP 子查询的 `cached` 逐一向上传。因此请求轨迹里的 `cached=false` 也不能证明底层没有命中缓存；当前 `MCPToolManager` 没有对外提供逐次缓存命中记录，若要分析每个子查询的缓存效果，需要增加专门埋点。

| 场景 | 上层能看到的结果 | 需要怎样解释 |
| --- | --- | --- |
| 模型没有发起检索工具调用 | `knowledge_used=false`，工具列表中无 `search_knowledge_base` | 本轮没有走知识库；这可能是模型选择，也可能是问题本身无需检索 |
| 查到真实片段 | 工具结果含文档列表，`knowledge_used=true` | 还需看最终回复是否正确使用片段，不能只看调用标记 |
| 底层超时、异常或熔断，fallback 生效 | 工具结果可能带 `fallback=true` 的降级说明，`knowledge_used=true` | MCP 会把 fallback 包装为成功，轨迹的 `result_success` 可能为 `true` |
| 全部子查询无结果 | `search_with_rewrite()` 返回失败和空列表 | Agent 收到失败工具结果后自行决定如何解释或追问 |

知识库调用超时、异常或熔断时，`knowledge_search` fallback 可能返回一条带 `fallback=true` 的“知识库降级结果”。MCP 层将这个结果包装为成功，所以上层 `result_success=true` 也不能单独证明真实检索成功。当前请求轨迹没有保存结果正文或 fallback 标记；验证知识内容需查看 `/search` 返回、MCP 日志或知识库数据。

## 6. 知识库导入：稳定 ID 与重复导入幂等

**代码**：`mcp/knowledge_base.py` 中的 `add_documents()`、`_chunk_text()` 和 `api/main.py` 的 `/knowledge/add`、`/knowledge/upload`。

长文档按句号和换行切成约 500 字片段；单个超长句可能超过 500 字。片段 ID 由标题、序号和片段前 50 字的 MD5 生成，写入使用 ChromaDB `upsert`。同一标题、相同切片再次导入时不会因为 ID 已存在而报冲突。接口返回的 `added_chunks` 是本次处理片段数，不是净新增数。若修改内容导致 ID 变化，旧片段不会自动清理，这一点需要在维护知识库时留意。

用一个两片文档说明返回值：首次导入标题“退款政策”的两片内容，`added_chunks=2`，总片段数增加 2；原样再次导入，`added_chunks` 仍为 2，但总数通常不增加。若把第 1 片的前 50 字改掉，它的 ID 会变化，旧片可能保留，新片又被写入；若只改第 1 片第 50 字之后的内容，ID 不变，`upsert` 更新该 ID 的内容和向量。当前接口没有“按标题删除旧版本再导入”的步骤，所以不能把 `upsert` 理解为完整的文档版本替换。

知识库使用独立 `knowledge_base` collection，与情景记忆、画像分开。ChromaDB 自身在写入和查询时生成向量；代码没有为知识库显式调用 Anthropic Embedding API。启动时只有 collection 为空才加载默认文档。文件上传限制 10 MB；`.json` 按文档数组解析，其他后缀当前按 UTF-8 文本导入。导入后没有主动清空 MCP 的检索缓存，同一个 query 短时间可能仍命中旧缓存。

## 7. 三级记忆：读写、压缩和画像更新

**代码**：`memory/conversation_memory.py`，入口在 `api/main.py` 的 `/chat`。

Redis 工作记忆按 `wm:{user_id}:{conv_id}` 存当前会话消息，TTL 24 小时；摘要存在 `summary:{user_id}:{conv_id}`。ChromaDB `episodic` 存压缩后的历史摘要，`user_profile` 存用户画像。新请求读取最多 20 条工作消息，以当前消息检索同会话情景记忆；不足时扩大到同用户其他会话。最终 prompt 最多放入 3 条相关历史和 8 条最近消息，意图识别只取最近 5 条作为历史。

`COMPRESS_AT=15` 是**消息条数**，不是 15 轮。每次 `/chat` 分别写用户和助手消息；从空会话开始，第 8 轮写入用户消息时就可能达到 15 条并同步压缩。压缩保留最近 5 条，旧消息交给 LLM 总结，摘要与旧摘要合并写回 Redis，并尝试写入 `episodic`。摘要生成或情景写入失败时有相应降级与日志；压缩仍会继续保留最近消息。

按时间顺序看第 8 轮：前 7 轮已有 14 条消息；第 8 轮 Agent 完成回复后，`/chat` 先写用户消息，列表变成 15 条，立即把前 10 条压缩，保留最近 5 条；然后才写本轮助手回复，列表变成 6 条。因此本轮 HTTP 请求的实际等待时间可能包含摘要 LLM 调用，但响应里的 `latency_ms` 取自 Orchestrator 执行，不包括 `/chat` 后续的记忆写入和压缩耗时。摘要和工作消息的 Redis TTL 均为 24 小时；情景记忆依赖 ChromaDB 写入成功。

HTTP `/chat` 写完两条消息后，以 `asyncio.create_task()` 更新用户画像。任务读取当前会话最近消息与已有画像，请求 LLM 提炼偏好和实体，再按用户 ID 存入 ChromaDB。它不阻塞当前响应，也没有在关闭服务时专门等待。画像是模型推断结果，不能当成经过人工核验的客户资料。

## 8. Skills：按角色和关键词注入处理规范

**代码**：`core/skill_loader.py`，Agent 的 `_build_system_prompt()`，以及 `GET /skills`、`POST /skills/reload`。

SkillManager 启动时扫描 `ECHOMIND_SKILLS_DIR`（默认 `skills/`）。普通 Agent 每次构造 system prompt 时，用当前消息和 Agent 类型筛选已启用 Skill，匹配关键词后加入 `[动态 Skills]`，并受 `ECHOMIND_SKILLS_MAX_PROMPT_CHARS` 控制。当前内置通用、技术、账单三类规范；并行回复的 ResponseComposer 还可能读取通用规范作为输出边界。热加载重新扫描文件，不需要重启 HTTP 服务。

例如消息“登录一直报 401”路由到 TechnicalAgent：`skills/technical_support/SKILL.md` 的 `agents: technical` 与当前角色匹配，关键词 `401` 也命中，所以技术排障规范进入本轮 system prompt；Billing 的 Skill 虽可能有类似“支付失败”等业务词，但 `agents: billing` 与当前角色不符，不会给 TechnicalAgent 注入。若同一句还涉及扣款并使 BillingAgent 成为辅助 Agent，BillingAgent 会用同一消息独立匹配自己的 Skill。`/skills/reload` 只更新加载结果；是否真的注入仍要同时满足角色、启用状态和关键词条件。

Skills 用来描述处理步骤、信息收集和安全边界；知识库保存退款政策、故障说明等事实片段。Skill 注入本身不会执行外部操作。EscalationAgent 当前直接生成交接回复，不走普通 Agent 的 system prompt 构建，因此不会动态注入 Skill。

## 9. Monitor：单实例部署下也能影响路由

**代码**：`monitor/performance_monitor.py` 的 `_collect()`、`_routing_penalty()`，以及 Orchestrator 的 `_monitor_degraded()`。

Monitor 默认每 10 秒读取 Agent 和 MCP 工具统计。Agent 成功率低于 `0.90` 时最多增加 `0.5` 惩罚，平均耗时超过 3000 ms 时最多再加 `0.4`，总惩罚不超过 `0.9`。采样值回写每个 Agent 的 `monitor_penalty`；同类多实例时，该值进入实例评分：

```text
routing_score = (success_rate × 0.7 + 1 / (1 + avg_ms / 1000) × 0.3)
                × (1 - monitor_penalty)
```

当前每类默认只有一个实例，仅靠“同类择优”不会改变专业类型选择。因此 Orchestrator 另有**类型级回退**：Technical 或 Billing 的全部实例惩罚值达到 `ECHOMIND_MONITOR_FALLBACK_PENALTY`（默认 `0.5`）时，本次领域候选排除该专业类型，路由原因追加 `monitor_fallback=[...]`。General 与 Escalation 不参与这个类型级回退。告警与建议是观测信息；是否实际回退，要看惩罚值和本次 `routing_reason`。

可以手算一次采样：某 Technical 实例成功率 `0.60`、平均耗时 `4000 ms`，成功率惩罚是 `min(0.5, (0.90-0.60)×2)=0.5`，延迟惩罚是 `min(0.4, (4000-3000)/10000)=0.1`，合计 `0.6`。默认阈值 `0.5` 下，若该类型只有这一实例，**下一次完成 Monitor 采样后**的路由会排除 Technical；若还有另一健康 Technical 实例，该类型继续可选并在实例池内择优。成功率 `0.85`、耗时 `4000 ms` 时惩罚只有 `0.1+0.1=0.2`，虽可能触发成功率告警，却没有达到类型回退阈值。

## 10. 端到端评测：精确意图与回复质量分开看

**代码**：`evaluation/evaluator.py`，接口 `POST /eval/run`。

意图评测逐条比较最终**细意图**与标注，计算 Accuracy、每类 Precision/Recall/F1 和 Macro-F1。对话评测用 Orchestrator 真实生成单轮或多轮回复，再由 LLM Judge 给 relevance、accuracy、completeness、helpfulness 四项 0～1 分；四项均值达到 `0.75` 视为该轮通过。意图汇总项以 Accuracy `0.75` 为通过线。Judge 失败时给四项 `0.5`，并记录失败标记，因此评测报告应结合 metadata 解读。

报告与上一次运行或持久化 baseline 比较，某指标相对下降超过 `5%` 才列为 regression；运行后尝试保存当前报告为新 baseline。评测用例直接调用 Orchestrator，评测器用本地历史维持多轮上下文；它**不走 `/chat` 的 Redis/ChromaDB 记忆读取与画像更新**。因此评测分数可以用于回归，但不能直接当作完整生产会话体验的证明。

评测结果应分开读：即使 `intent_accuracy=0.91`，`technical_login` 的单类 F1 仍可能很低，说明总体准确率掩盖了登录故障细类的问题。`IntentEvaluator` 内部会计算 `per_class`，但当前 `/eval/run` 响应只暴露总体 Accuracy、Macro-F1 和 metadata 中逐条 `cases`；要分析某类误判，可先查看 `cases`，单类 F1 需直接使用内部评测结果或扩展接口。如果某轮 Judge 的四项均为 `0.5` 且 `metadata.judge_failed=true`，这是评分调用失败后的默认值，不能解释成模型回答“恰好中等水平”。回归比较的是当前指标相对上一次或 baseline 的变化，例如 `0.80 → 0.75` 的相对下降是 `6.25%`，会进入 `regressions`；`0.80 → 0.77` 只下降 `3.75%`，不会进入。当前运行结束后会尝试覆盖 baseline 文件，排查长期趋势时需要另行保存历史报告。

## 11. 面试或项目展示时的准确表述

- **意图识别**：三路加权后先按 `intent_group` 汇总，再选组内具体意图；Pattern 只能同组细化。可以展示 `billing` 单项高于技术单项、却低于技术组总分的可复算例子。
- **Agent 路由**：一个最终意图决定主要倾向，关键词和实体补足复合领域；主辅并行后由 Composer 生成一条回复。升级节点当前输出交接信息和标记。
- **RAG**：模型通过 `search_knowledge_base` 工具按需调用；MCP 层执行查询改写、并行召回、去重、重排、缓存和 fallback。`knowledge_used` 只表示调用记录。
- **工程修复**：工具状态改为请求局部，减少共享 Agent 并发串数据；轨迹按 `request_id` 暴露；知识库用稳定 ID + `upsert` 处理重复导入；Monitor 在单实例部署下通过类型级回退影响后续路由。
- **可验证范围**：用 `/chat` 看路由和 `request_id`，用 `/trace/tool/{request_id}` 看工具调用，用 `/search` 看检索结果，用 `/monitor` 看降权与统计，用 `/eval/run` 看评测结果。当前没有真实订单、退款和工单系统集成。
