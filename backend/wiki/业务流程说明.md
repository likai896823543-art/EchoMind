# EchoMind 业务流程说明（按当前代码）

本文档描述当前代码实际执行的客服流程。

图中的黄色节点表示条件判断；不同箭头标明实际执行分支。每张图后面的文字给出阈值、字段和失败处理细节。

## 1. `/chat` 从请求到响应

![/chat 请求主流程图](assets/flows/01-chat-flow.png)

图中没有“按意图先查知识库”节点：Agent 执行期间是否使用 RAG，取决于模型是否发起 `search_knowledge_base` 工具调用。

`POST /chat` 接收 `message`、`user_id`（默认 `anonymous`）和可选的 `conv_id`。未传 `conv_id` 时生成 UUID；服务未初始化时返回 HTTP 503。一次正常请求按以下顺序执行：

1. **读记忆**：按 `user_id + conv_id` 读取 Redis 最近消息和摘要；以当前消息检索 ChromaDB 情景记忆，再读取该用户画像。`MemoryContext.to_prompt_text()` 将摘要、最多 3 条相关历史、画像和最多 8 条最近消息拼成背景文本。
2. **识别意图**：从工作记忆的最后 5 条构造 `history`，调用 Orchestrator 持有的 `IntentRecognizer`。结果包括细意图、`intent_group`、融合置信度、紧急度、实体和各来源原始置信度。
3. **构造请求**：把原消息、背景文本、历史、实体和意图结果放进 `Request`。`Request` 自带 `request_id`，之后可用它查询工具轨迹。
4. **编排**：`AgentOrchestrator.run()` 先处理低置信度澄清，再决定主 Agent 和辅助 Agent。单 Agent 直接执行；复合问题并行执行，并由 ResponseComposer 合成回复。
5. **写记忆**：先写用户消息，再写最终回复。每写一条都会刷新 Redis 24 小时 TTL；达到压缩阈值时就在该次写入过程中压缩。
6. **更新画像**：用 `asyncio.create_task()` 启动画像提炼，当前 HTTP 响应不等待它完成。画像更新失败只记录日志。
7. **返回**：响应含回复、意图及组、Agent 路由信息、`tools_used`、`knowledge_used`、实体、意图置信度、升级标记和耗时。

**RAG 不在第 2 步和第 4 步之间预先执行。** `/chat` 给 Agent 注册 `search_knowledge_base` 工具，由模型在执行时自行决定是否调用。没有工具调用，就没有本轮知识库检索，也不会把 Top-K 内容预先塞入背景。

## 2. 意图识别：三路结果怎样合并

### 2.1 三路各做什么

| 来源 | 当前实现 | 输出 |
| --- | --- | --- |
| LLM | 带细意图列表和最近历史请求模型，解析其 JSON | 一个意图、置信度、reasoning；异常时标记 `failed` |
| Embedding | 首次请求懒加载各意图模板向量，对消息与模板做余弦相似度 | 相似度最高的一个意图及分数 |
| Pattern | 先找细意图关键词；没有细意图命中才找粗意图关键词 | 命中意图及 `min(1, 0.5 + 0.25 × (命中数 - 1))` |

LLM 与 Embedding 任务并行，Pattern 同步完成。Embedding 路径会先尝试客户端提供的 `embeddings.create`；当前客户端没有该资源或远端失败时，用本地 256 维字符 1～3 gram 哈希向量。它不等同于知识库使用的 ChromaDB 默认 Embedding。模板向量在识别器实例中缓存，识别结果另有最多 1000 条的内存缓存；缓存键由当前消息和最多 3 条历史组成。

### 2.2 加权、分组和阈值

![三路意图融合与阈值流程图](assets/flows/02-intent-fusion.png)

“同组细化条件”是：组内当前获胜意图为粗意图、Pattern 是同组细意图、Pattern 置信度至少 `0.5` 且组分数低于 `0.8`。图中阈值默认 `0.5`；LLM 失败分支不走分组投票。

正常情况下，LLM / Embedding / Pattern 权重为 `0.7 / 0.2 / 0.1`；禁用 Embedding 时为 `0.85 / 0.15`。先计算每个细意图或粗意图的加权得分，再把同一 `intent_group` 内的得分相加，**先选最高分的组，再选组内得分最高的具体意图**。例如 `technical` 与 `technical_login` 属于同组，两者的加权分数先合并与 `billing` 组比较；不会仅因 `billing` 单项分数最高就忽略技术组的合计分。

分组关系包括：`order_status`、`logistics` → `query`；`refund`、`invoice`、`payment_issue` → `billing`；`account_security` → `account`；`technical_login`、`technical_crash` → `technical`；`human_handoff` → `escalation`。其他意图的组就是自身。

一个可复算的例子：假设将阈值配置为 `0.2`，LLM 报 `billing/0.30`、Embedding 报 `technical_login/0.90`、Pattern 报 `technical/0.40`，则三路加权分分别为 `billing=0.21`、`technical_login=0.18`、`technical=0.04`。虽然账单的单项 `0.21` 高于任一技术单项，技术组总分 `0.22` 仍高于账单组 `0.21`，最终选技术组内的 `technical_login`。默认阈值为 `0.5` 时，这组较弱证据会返回 `other`；分组胜出与是否过置信度阈值是两步判断。

如果组内先选出粗意图，Pattern 给出置信度至少 `0.5` 的细意图，且**细意图与获胜组相同**、组分数低于 `0.8`，则用 Pattern 细化。由此 `billing` 不会被跨领域改成 `technical_login`。细化时返回置信度取组分数和 Pattern 置信度的较大值。否则，获胜组分数低于默认阈值 `0.5` 时返回 `other`；达到阈值才返回组内获胜意图。LLM 失败是单独的兜底分支：优先采用有正分的 Embedding 结果，再采用 Pattern 结果，不经过上述加权合并。

`source_scores` 返回三路**原始**置信度；发生 Pattern 细化时额外写入 `refined_by_pattern`，它不是三个权重乘积的明细。最终 `intent_group` 从最终意图重新映射得到。

### 2.3 实体、紧急度和低置信度澄清

实体按规则从原消息提取：订单号、日期、金额、4xx/5xx 错误码；`product` 当前固定为空列表。这些实体进入 Agent 输入包，并参与领域打分。紧急度按关键词判断：`紧急`、`urgent`、`asap`、`立刻` 为 CRITICAL；`今天`、`马上`、`尽快` 等为 HIGH；`这周`、`soon`、`快点` 等为 MEDIUM。没有关键词时，`escalation` / `human_handoff` 为 HIGH，`complaint` 为 MEDIUM，其余为 LOW。**HIGH 本身不会直接切换到 EscalationAgent；CRITICAL 会。**

只有最终意图是 `other`、去空格后消息长度大于 2、且置信度小于 `0.5`，Orchestrator 才直接返回澄清问题，询问订单物流、退款账单、账户资料或技术故障。此分支不调用 Agent 或 RAG，但仍记录一条空工具轨迹，并经 `/chat` 写入对话记忆。长度不超过 2 的 `other` 继续正常路由。

## 3. Agent 路由：主处理、辅助处理、升级

![主辅 Agent 路由与升级流程图](assets/flows/03-agent-routing.png)

EscalationAgent 在当前实现中只生成交接文本；它不会调用人工客服系统。Monitor 的专业类型过滤发生在确定主辅 Agent 之前。

### 3.1 先处理强制升级

`urgency == CRITICAL` 直接选择 EscalationAgent，路由置信度为 `1.0`。否则，意图为 `escalation` 或 `human_handoff` 也直接选择 EscalationAgent。EscalationAgent 当前是确定性节点，不调用 LLM 或工具：它返回升级原因、已记录实体和安全提示，`escalated=true`。这一步只是客服交接文本与标记，不会真正创建工单。普通投诉意图 `complaint` 默认仍进入领域打分；只有命中升级意图、CRITICAL 或回复中出现升级关键词等条件，才会在最终结果中标记升级。

### 3.2 三个业务领域怎么打分

非强制升级请求给 General、Technical、Billing 三类打分。General 基础分 `0.1`；属于查询、订单、物流、请求、投诉、问候、反馈、other 的意图加 `0.55`。技术粗细意图给 Technical 加 `0.75`；账单、退款、发票、支付、账户及账户安全意图给 Billing 加 `0.75`。消息关键词另加分：每个技术或账单命中加 `0.18`，各最多加 `0.45`；通用关键词每个加 `0.12`，最多加 `0.35`。提取到错误码再给 Technical 加 `0.2`，金额给 Billing 加 `0.15`，订单号给 General 加 `0.1`。

例如“登录报错 401，而且这个月重复扣款”：技术侧有 `报错`、`401` 和错误码实体，账单侧有 `扣款`，因此即使意图识别只返回一个主意图，路由仍能发现两个领域。主 Agent 是可用领域中分数最高者；相同分数时遵循代码中的候选插入顺序。`routing_confidence` 是主领域分数截到 `1.0`，**不是意图识别置信度**。`routing_reason` 会写出意图、组、主辅 Agent 和各可用领域分数。

细意图在这里的实际作用是：给对应领域加 `0.75`、进入角色输入包和返回字段；例如 `technical_login` 与 `technical_crash` 都路由到 TechnicalAgent，但模型能看到具体意图。细意图本身不会触发不同知识库，也不会作为是否调用 RAG 的硬开关。

### 3.3 什么时候并行

`_collaboration_targets()` 独立检查技术和账单的明确意图或关键词。若命中另一个专业领域，且它有实例并未被监控判为降级，就加入 `supporting_agents`；主 Agent 不重复加入，General 不作为辅助 Agent。如果没有明确的复合信号，按分数兜底：非主专业领域分数至少 `0.45`，且至少达到主分数的 `55%`，才加入辅助。故“有技术 + 账单信号”可以并行，并非机械要求两个领域分数都超过同一个固定阈值。

并行时对主辅 Agent 调用 `_execute()`，用 `asyncio.gather(..., return_exceptions=True)` 收集结果。ResponseComposer 只取成功且非空的回复：一条成功回复就直接返回；多条则再调用 LLM 去重、处理冲突并生成一条面向用户的中文回复；Composer 失败时用“主回复 + 补充说明”确定性拼接。**最终用户文本通常不会显示 `[technical - 主处理]` 之类的 Agent 标签。**所有成功执行的 `tools_used` 去重汇总，工具调用明细逐条合并到本次轨迹。若全部失败，返回“抱歉，所有 Agent 均处理失败。”

### 3.4 不可用、执行失败和监控降级

每类 Agent 当前默认一个实例；若未来同类有多个实例，`_best_agent()` 用运行时评分选实例：`(成功率 × 0.7 + 1/(1 + 平均耗时秒数) × 0.3) × (1 - monitor_penalty)`。初始无调用时成功率按 `1.0` 算。

目标类型没有实例时 `_execute()` 尝试 GeneralAgent。Technical 或 Billing 执行失败时也重试 GeneralAgent；General 与 Escalation 执行失败不会再转给别的 Agent。`BaseAgent.handle()` 将模型异常转换成通用错误回复和 `success=false`，不承诺一定得到有效业务答案。

监控还可在**选领域时**回退：当某专业类型的所有实例 `monitor_penalty` 都达到阈值（环境变量 `ECHOMIND_MONITOR_FALLBACK_PENALTY`，默认 `0.5`）时，从本次可选领域中排除。该类型即使由意图和关键词命中，也不会作为主或辅助 Agent；路由原因附带 `monitor_fallback=[...]`。General 和 Escalation 不参与这项领域回退。阈值可以调整，但监控采样不是对每次请求立即同步触发。

## 4. Agent 怎样决定是否调用 RAG

![Agent 工具调用与 RAG 流程图](assets/flows/04-rag-tool-flow.png)

模型直接回复时没有 RAG。`knowledge_used=true` 仅表示调用过 `search_knowledge_base`，检索失败后的 fallback 也可能使它为 `true`。

### 4.1 工具由模型选择，不按意图预取

API 启动时注册 MCP 工具 `knowledge_search`，再给所有 Agent 注入共享的 `search_knowledge_base` 工具描述。General、Technical、Billing 同时拥有各自的本地工具白名单，例如请求上下文检查、错误码查询、诊断计划、账单字段检查；EscalationAgent 虽配置了工具范围，但其 `handle()` 当前不调用模型，因此不会实际调用 RAG。

普通 Agent 在 `_call_llm()` 把记忆背景、结构化实体、角色输入包和本轮消息组织为模型消息，并提供工具 schema。模型可直接回复，也可返回 `tool_use`。只有出现 `search_knowledge_base` 的 `tool_use`，才执行 RAG；`greeting` 等意图并没有代码级禁用，技术意图也没有代码级强制检索。一次请求最多经历 3 轮模型/工具往返；超过轮数按 Agent 失败处理。

`search_knowledge_base` 接收模型给出的 `query` 和可选 `top_k`（默认 5），调用 `MCPToolManager.search_with_rewrite("knowledge_search", ...)`。检索顺序是：

1. LLM 被要求生成 3 个不同角度的子查询，同时保留原 query；代码没有强制校验模型实际返回的条数。改写失败则只用原 query。
2. 各子查询并行调用 `knowledge_search`，每路至少召回 5 条。MCP 工具层先查 300 秒缓存，再检查熔断、参数和超时，最后执行 ChromaDB 查询。
3. 合并结果并按序列化内容哈希去重；全部无结果则工具返回失败。
4. 合并结果多于 `top_k` 时用 LLM 排序，失败则取原顺序前 `top_k`；结果数量不超过 `top_k` 时直接返回。`reranked` 表示走过这条重排链路，不能单凭它证明排序质量提升。
5. 工具结果作为 `tool_result` 回传模型，由模型写最终回复；代码没有自动把检索结果预拼入 system prompt。

`/search` 是独立检索入口，直接调用同一条“改写 → 召回 → 去重 → 重排”链路，不经过意图识别和 Agent；返回 `query`、`results`、`reranked`。在 `/chat` 中，`knowledge_used` 的判定是 `tools_used` 是否包含 `search_knowledge_base`，表示**调用过检索工具**，不保证查到有效文档或模型引用了结果。

### 4.2 故障与 fallback 的真实含义

`knowledge_search` 超时、异常或熔断时，注册的 fallback 产生一条标题为“知识库降级结果”的说明，带 `fallback=true`、`score=0` 和错误原因。MCP 层会把该 fallback 包装为 `ToolResult(success=True)`；因此上层 `search_knowledge_base` 也可能返回 `success=true`，但 `results` 实际只有降级提示。当前请求级工具轨迹**不保存结果内容或 fallback 标记**，且上层成功分支没有传递 MCP 的错误字段；因此不能仅凭 `knowledge_used=true`、轨迹中的 `result_success=true` 或空 `error` 认定检索成功。需要核对 MCP 日志或直接调用 `/search` 排查。查询改写失败可回退原 query；所有子查询都无结果则返回 `success=false` 和空列表。主对话仍由 Agent 根据工具返回继续处理。

## 5. 知识库导入与存储

知识库使用独立的 ChromaDB `knowledge_base` collection。初始化优先连接独立 ChromaDB 服务；连不上时尝试本地 `PersistentClient`。collection 为空才导入内置客服文档。文档按最多约 500 字的句子片段切分；切分以句号/换行为主，单个超长句可能超过 500 字，所以“500 字”不是严格上限。ChromaDB 在 `upsert` 和 `query` 时自动处理 Embedding；本模块未显式接入 Anthropic Embedding API。

- `POST /knowledge/add`：接收 `documents: [{title, content}]`，返回本次处理的片段数 `added_chunks` 和 collection 当前总数 `total_chunks`。
- `POST /knowledge/upload`：文件超过 10 MB 返回 413；`.json` 按文档数组解析，其他后缀目前也会作为 UTF-8 文本整篇导入，并非严格只允许 `.txt` / `.md`。文件名去扩展名后作为文本标题。
- `GET /knowledge/stats`：返回当前总片段数。

片段 ID 根据标题、片段序号和片段前 50 个字符生成稳定 MD5，写入用 `upsert`。因此重复导入**同一标题、同一切片内容**不会发生重复 ID 冲突；`added_chunks` 计的是本次写入片段数，并不等于净新增数。若文档改写导致 ID 改变，旧片段不会被此流程自动删除，可能同时留在库中。导入与查询共用 collection，但工具有 300 秒缓存；当前导入接口没有显式清空检索缓存，刚导入后相同查询可能短时间读到缓存结果。

## 6. 记忆、压缩和画像

![工作记忆压缩流程图](assets/flows/05-memory-compression.png)

画像更新是另一条后台任务：在 `/chat` 的两条消息写完后启动，读取当前会话和已有画像，再尝试写入 ChromaDB `user_profile`。它不在上图的同步压缩链中。

工作记忆使用 Redis 列表 `wm:{user_id}:{conv_id}`，最新消息在前，TTL 为 86400 秒。读时最多取 20 条并还原时间顺序。当前 `/chat` 每轮写两条消息；任一条写入后列表长度达到 `COMPRESS_AT=15`，就同步执行压缩。因此触发点是**消息条数**，不是 15 轮对话，也不是达到 `WORKING_MAX=20` 才开始压缩。

压缩时保留最近 5 条，把更旧的消息交给 LLM 总结为 2～3 句话。摘要生成失败时用“对话包含 N 条消息（摘要生成失败）”替代；新摘要与旧摘要合并后存入 `summary:{user_id}:{conv_id}`，TTL 24 小时。旧片段摘要尝试写入 ChromaDB `episodic`，写入失败只记日志。最后 Redis 列表重建为最近 5 条。后续上下文读取时，情景检索先限定当前用户和会话；不足 `HISTORY_TOP_K=5` 条再扩大到同一用户其他会话，去重后最多取 5 条，其中最多 3 条进入 prompt。

例如从空会话开始，前 7 轮各写一条用户消息和一条助手消息，共 14 条；第 8 轮写入用户消息后达到第 15 条，立刻压缩前 10 条并保留最近 5 条，然后该轮助手回复作为新消息继续写入。压缩发生在 `/chat` 返回前，所以这次请求的耗时可能包含一次摘要 LLM 调用。

画像更新发生在 `/chat` 写完用户和助手消息之后，以后台任务运行。它读取该会话最近最多 10 条工作记忆和已有画像，要求 LLM 生成 `preferences` 与 `entities` JSON，按用户 ID 存入 ChromaDB `user_profile`。画像是用户维度，同一用户不同会话可复用。任务失败不会阻塞当前 HTTP 响应；当前实现也没有在关停时专门等待这些画像任务。CLI 写工作记忆，但没有调用 `update_profile()`。

## 7. Skills 何时进入回复

启动时 `SkillManager` 从 `ECHOMIND_SKILLS_DIR`（默认项目 `skills/`）加载文件。`POST /skills/reload` 重新扫描并将管理器引用刷新到 Orchestrator、Composer 和 Agent；`GET /skills` 可查看已加载规则和解析错误。每次普通 Agent 构造 system prompt 时，以**当前消息**和 Agent 类型调用 `prompt_for()`：只有启用、Agent 范围匹配且关键词匹配的 Skill 才注入 `[动态 Skills]`。这不是路由器的独立判定，也不会使某个 Agent 自动执行退款、查单等后台操作。

当前内置通用、技术、账单三类处理规范。General、Technical、Billing 都在自己的角色契约之后插入匹配到的 Skill。并行协作的 ResponseComposer 还会尝试读取通用 Skill，约束最终整合文本。EscalationAgent 的确定性 `handle()` 不构造 system prompt，因此不会动态注入 Skill。

## 8. 工具调用轨迹怎样查看

普通 Agent 的每次 `tool_use` 都记录工具名、调用 Agent、工具调用 ID、输入、调用是否抛错、工具结果的 `success`、耗时、缓存/重排标记和错误文字。`tools_used` 是实际进入白名单工具 handler 的工具名；未知工具或参数校验失败会写入 `tool_traces`，但不会加入 `tools_used`。Agent 调用模型失败时，`AgentCallError` 保留失败前已有工具轨迹；请求级结果最终由 Orchestrator 汇总。

Orchestrator 在请求结束时将轨迹放入内存 `deque`，默认最多 200 条，可用 `ECHOMIND_TOOL_TRACE_MAX` 调整。`GET /trace/tool/{request_id}` 查单次，`GET /trace/tools?limit=20` 看最近记录。轨迹含 `request_id`、时间、意图、主辅 Agent、工具列表、调用明细、升级标记和耗时。低置信度澄清请求也会有记录，但工具列表为空。若专业 Agent 失败后 `_execute()` 成功调用 GeneralAgent，最终 `AgentResponse` 会替换原失败响应，原专业 Agent 的工具轨迹目前不会并入这条请求级轨迹，应查看日志和 Agent 统计排查。轨迹只在当前进程内存中，进程重启后不可查；多进程实例之间也不共享。`/chat` 的 `tools_used` 仅是工具名摘要，需用 `request_id` 查询详细轨迹。

## 9. Monitor 怎样影响下一次路由

`PerformanceMonitor` 启动后按 `MONITOR_INTERVAL` 采集，默认每 10 秒一次。它读取 Agent 总调用、成功率、平均耗时，以及 MCP 工具成功率、耗时、连续失败数；低于 Agent 成功率 `0.90`、工具成功率 `0.95`，或 Agent 平均耗时超过 3000 ms、工具超过 5000 ms 时产生告警。工具连续失败至少 3 次会产生排查建议。`ALERT_WEBHOOK_URL` 配置后告警会异步发送；未配置时只在内存和日志中体现。`/monitor` 返回统计、最近未解决告警和建议；`/metrics` 暴露当前 Prometheus 指标，另可通过 `PROMETHEUS_PORT` 启动独立指标端口。

每次采样对 Agent 计算 `monitor_penalty`：成功率低于 `0.90` 时增加最多 `0.5`，平均耗时高于 3000 ms 时增加最多 `0.4`，合计最多 `0.9`。该值回写到每个 Agent 实例。它一方面进入同类实例的 `routing_score()`，另一方面在全部专业实例惩罚达到默认 `0.5` 时让路由排除该专业类型，即使当前每类只有一个实例也能影响后续请求。告警和建议并不等于已经发生降级；是否降级以惩罚值和路由原因中的 `monitor_fallback` 为准。

## 10. 评测链路与运行入口差异

`POST /eval/run` 可传意图用例和单轮/多轮对话用例；某项未传就使用内置默认用例。意图评测逐条调用**独立的** `IntentRecognizer`，比较细意图精确值，计算 Accuracy、每类 Precision/Recall/F1 和 Macro-F1。对话评测逐轮调用同一个 Orchestrator，传入评测器维护的短历史，再用 LLM Judge 对相关性、准确性、完整性、有用性各打 0～1 分。四项均值至少 `0.75` 才算该轮通过；意图评测准确率至少 `0.75` 才算其汇总项通过。Judge 异常会给四项 `0.5`，并在 metadata 中标出失败。

报告计算通过率和平均分，并与上一次运行或磁盘 baseline 比较；某指标相对下降超过 `5%` 才列入 `regressions`。每次运行后尝试把当前报告写成新 baseline。评测对话直接走 Orchestrator，**不走 `/chat` 的 Redis/ChromaDB 记忆读取和画像更新**；它能调用 Orchestrator 已注册的工具，但多轮上下文由评测器本地 `history` 提供。

CLI 使用 `api/main.py --cli` 独立创建 Orchestrator、SkillManager 和 MemoryManager，读取并写入会话记忆，意图识别交给 `run()` 内部处理。CLI 当前没有创建 MCPToolManager 或注册知识库工具，也没有启动 Monitor 和画像后台更新。因此 CLI 与 `/chat` 的 Agent 路由主逻辑相同，但不能据 CLI 的结果判断在线 `/chat` 的 RAG、监控或工具轨迹 API 行为。

## 11. 典型输入的实际分支

| 输入或条件 | 代码中的处理 | 需要核对的输出 |
| --- | --- | --- |
| “你好” | 通常落到 General；模型可直接回答 | `agent_type`、意图及置信度；不能假定一定查知识库 |
| “登录报错 401” | 技术意图、关键词和错误码给 Technical 加分 | `primary_agent=technical`、`entities.error_code`、是否真的调用工具 |
| “退款多久到账” | 退款细意图归入账单组，Billing 分数提高 | `intent=refund`、`intent_group=billing`；RAG 由模型决定 |
| “登录报错 401，还重复扣款” | 技术和账单两领域分别打分，可能形成主辅并行 | `primary_agent`、`supporting_agents`、Composer 后的一条回复 |
| “转人工” | 命中升级意图时执行确定性交接节点 | `escalated=true`；没有真实工单编号 |
| 最终 `other` 且低置信度、消息长度 >2 | 直接澄清 | `routing_reason` 为低置信度澄清，工具轨迹为空 |
| 单个专业 Agent 失败 | `_execute()` 尝试 General 兜底 | `agent_type` 可能是 `general`，原专业 Agent 的失败需看日志/统计 |
| 工作消息达到 15 条 | 当前写入过程中压缩，保留最近 5 条 | Redis 摘要与 episodic 尝试写入情况 |
| 知识库不可用但模型调用了检索工具 | MCP fallback 交回降级说明 | `knowledge_used` 仍可能为 `true`，不能当作检索成功 |
