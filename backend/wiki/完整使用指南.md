# EchoMind 完整使用指南

本文档说明 EchoMind 的部署、启动、API 调用、知识库使用、ChromaDB 数据查看、监控评测和常见排障。

重要说明：EchoMind 当前已经支持可直接调用的端到端评测能力。启动 HTTP 服务后，可以通过 Swagger 或 `curl` 调用 `POST /eval/run`，自动评测意图识别准确率、端到端 Agent 回复质量、LLM-as-Judge 四维评分、回归检测和优化建议。该能力不是文档设计稿，而是由 `evaluation/evaluator.py` 和 `api/main.py` 中的 `/eval/run` 接口真实实现。

EchoMind 是一个企业级智能客服系统，核心链路为：

```text
用户请求
  -> FastAPI /chat
  -> MemoryManager 读取 Redis 工作记忆 + ChromaDB 情景记忆 + 用户画像
  -> IntentRecognizer 识别细粒度意图 + 意图组 + 结构化实体
  -> AgentOrchestrator 按意图、关键词、实体打分，确定主辅 Agent
     - 低置信度 other 且消息超过 2 字：先澄清
     - CRITICAL / 转人工意图：EscalationAgent 交接回复
     - 技术 + 账单复合问题：主辅 Agent 并行，Composer 合成
  -> SkillManager 按消息关键词和 Agent 类型匹配 Skills
  -> 普通 Agent 基于记忆 + 实体 + Skills 调用 LLM
     - 模型直接回复，或自行调用 search_knowledge_base 等工具
     - 若调用 RAG：查询改写 -> 并行召回 -> 去重 -> 重排 -> 工具结果回传模型
  -> 记录 request_id 对应的工具调用轨迹
  -> 写入 Redis，达到 15 条消息时压缩；异步更新 ChromaDB 用户画像
```

除主对话链路外，系统还提供独立评测链路：

```text
评测请求
  -> FastAPI /eval/run
  -> IntentEvaluator 计算 Accuracy / Macro-F1
  -> EndToEndEvaluator 调用 Orchestrator 生成真实 Agent 回复
  -> LLMJudge 从相关性、准确性、完整性、有用性四个维度评分
  -> 与历史基线对比，输出 regressions 和 recommendations
```

## 1. 项目结构

```text
EchoMind/
├── api/main.py                    # FastAPI 入口，含 /chat /search /trace /knowledge /monitor /eval
├── core/intent_recognizer.py      # 三路融合意图识别、细粒度意图、实体提取
├── core/skill_loader.py           # Skills 加载、解析、匹配和 prompt 注入
├── agents/agent_orchestrator.py   # 多 Agent 路由编排
├── agents/tools.py                # Agent 工具白名单与共享 RAG 工具
├── memory/conversation_memory.py  # Redis + ChromaDB 记忆管理
├── mcp/tool_manager.py            # MCP 工具调用、查询改写、重排、熔断、缓存、降级
├── mcp/knowledge_base.py          # ChromaDB RAG 知识库
├── monitor/performance_monitor.py # Agent/工具在线监控
├── evaluation/evaluator.py        # 端到端评测
├── skills/                        # 可热加载的客服 Skills 文档
│   ├── general_customer_service/  # 通用客服接待规范
│   ├── technical_support/         # 技术支持处理规范
│   └── billing_support/           # 账单退款处理规范
├── data/demo_docs/                # 演示知识库文档
├── docker-compose.yml             # Docker 全栈编排
├── Dockerfile
├── requirements.txt
└── .env                          # 本地配置文件，需自行创建；不要提交密钥
```

## 2. 环境准备

### 2.1 必需依赖

- Docker
- Docker Compose
- Anthropic API Key，或兼容 Anthropic 协议的第三方 API Key

### 2.2 配置 `.env`

当前仓库没有 `.env.example`。若项目根目录尚无 `.env`，可创建最小配置；若文件已存在，请直接编辑它，不要用下列命令覆盖已有密钥或配置：

```bash
if [ ! -e .env ]; then
  printf 'ANTHROPIC_API_KEY=replace_with_your_key\n' > .env
fi
```

如果使用兼容 Anthropic 协议的服务，按服务商实际提供的地址和模型名补充：

```env
ANTHROPIC_BASE_URL=https://your-compatible-endpoint.example
ANTHROPIC_MODEL=your-model-name
```

Docker Compose 会覆盖 `REDIS_URL` 为容器内 Redis 地址。`CHROMA_HOST` 和 `CHROMA_PORT` 若不设置，应用默认使用 `chromadb:8000`；不要把宿主机访问地址 `localhost:8001` 写进应用容器环境。Redis 密码默认来自 Compose 的 `REDIS_PASSWORD`：

```env
REDIS_PASSWORD=echomind123
```

Skills 默认从项目内 `./skills` 读取，也可以通过环境变量覆盖：

```env
ECHOMIND_SKILLS_DIR=./skills
ECHOMIND_SKILLS_MAX_PROMPT_CHARS=5000
```

### 2.3 HTTP 服务与 CLI 的区别

| 入口 | 启动方式 | 当前能力 |
| --- | --- | --- |
| HTTP API | `docker compose up -d --build` | `/chat`、知识库工具、监控、工具轨迹接口、画像后台更新、评测接口 |
| CLI | `docker compose run --rm echomind python api/main.py --cli` | 交互聊天、意图识别、Agent 路由、Skills、Redis/ChromaDB 会话记忆 |

CLI 会另建 Orchestrator 和 MemoryManager；它**没有初始化共享 RAG 工具、Monitor 或画像后台更新**，也不暴露 HTTP 轨迹查询接口。要验证 RAG 工具或监控反馈，请调用 HTTP `/chat`。两种入口都需要可用的模型服务、Redis 和 ChromaDB。

## 4. 交互式 CLI 与本地源码调试

在项目根目录运行 CLI：

```bash
docker compose run --rm echomind python api/main.py --cli
```

Compose 会使用同一网络和 `.env`，也会按 `depends_on` 等待 Redis、ChromaDB 健康检查。输入 `quit`、`exit`、`退出` 或空行结束会话。该命令运行的是构建进镜像中的代码；修改 Python 源码后先执行 `docker compose build echomind` 再运行。Compose 只挂载了 `skills/`、`data/` 和 `logs/` 等目录，代码本身没有热挂载。修改 Skill 文件后，HTTP 服务可调用 `/skills/reload`；CLI 重新启动时会重新加载 Skills。

如需直接在宿主机运行 `python api/main.py --cli`，需先安装 `requirements.txt`，确保 Redis 可从宿主机访问，并配置 `REDIS_URL`、`CHROMA_HOST=localhost`、`CHROMA_PORT=8001` 及可写的 `CHROMA_PERSIST_DIRECTORY`。应用先连接 ChromaDB 服务；连接失败时会尝试本地持久化模式。宿主机 CLI 不能用容器网络里的 `redis`、`chromadb` 主机名。

## 5. Swagger 和接口总览

EchoMind 基于 FastAPI 构建，启动 HTTP 服务后可以直接在浏览器访问 Swagger UI 调用接口。

本地 Swagger 地址：

```text
http://localhost:8000/docs
```

如果使用 Nginx 反向代理：

```text
http://localhost/docs
```

打开 Swagger 后，可以点击任意接口右侧的 **Try it out**，填写参数后点 **Execute** 直接调用本地服务。常用调试顺序：

```text
1. GET /health                确认服务是否就绪
2. POST /chat                 测试主对话链路
3. GET /knowledge/stats       查看知识库是否已有数据
4. POST /knowledge/upload     上传演示知识库文件
5. POST /search               测试知识库检索、查询改写和重排
6. GET /monitor               查看 Agent 和工具运行指标
7. GET /skills                查看当前已加载 Skills
8. POST /skills/reload        修改 Skill 文件后热加载
9. GET /metrics               查看 Prometheus 指标文本
10. POST /eval/run            运行端到端评测
11. GET /trace/tools           查看最近请求的工具调用轨迹
12. GET /trace/tool/{request_id} 追查一次 /chat 的工具调用
```

### 5.1 接口总览

| 方法 | 路径 | 参数位置 | 作用 | 适合场景 |
|------|------|----------|------|----------|
| `GET` | `/health` | 无 | 健康检查，返回服务状态和 Agent 统计 | 启动后确认服务可用 |
| `POST` | `/chat` | JSON Body | 主对话接口，完成记忆读取、意图识别、Agent 路由、回复生成、记忆写入 | 业务主链路 |
| `GET` | `/trace/tools` | Query 参数 `limit` | 查看当前进程保存的最近工具调用轨迹 | 排查模型是否调过工具 |
| `GET` | `/trace/tool/{request_id}` | 路径参数 | 查看一次请求的工具调用明细 | 用 `/chat` 返回的 `request_id` 追踪 |
| `GET` | `/monitor` | 无 | 查看 Agent/工具统计、告警和优化建议 | 观察在线表现 |
| `GET` | `/metrics` | 无 | 暴露 Prometheus 指标文本 | Prometheus 抓取和排查监控 |
| `POST` | `/search` | Query 参数 | 执行知识库检索优化链路：查询改写、并行召回、合并去重、LLM 重排 | 测试 RAG 检索 |
| `GET` | `/skills` | 无 | 查看当前加载的 Skills、适用 Agent、关键词和解析错误 | 确认动态规则是否生效 |
| `POST` | `/skills/reload` | 无 | 运行时重新扫描 Skill 目录 | 修改业务规范后无需重启 |
| `POST` | `/knowledge/add` | JSON Body | 批量导入文档到 ChromaDB 知识库 | 程序化导入文档 |
| `POST` | `/knowledge/upload` | Form File | 上传文件导入知识库；`.json` 解析为文档数组，其他后缀按文本处理 | 手动上传知识库文件 |
| `GET` | `/knowledge/stats` | 无 | 查看知识库文档片段总数 | 确认知识库是否有数据 |
| `POST` | `/eval/run` | 可选 JSON Body | 运行内置或自定义意图识别和端到端对话评测 | 演示 LLM-as-Judge 评测 |
| `GET` | `/docs` | 浏览器访问 | Swagger UI | 浏览和调试所有接口 |

### 5.2 Skills 动态能力加载

Skills 是可热加载的业务规则文档，用来把通用客服、技术支持、账单退款等规范动态注入对应 Agent 的 system prompt。它和知识库的定位不同：知识库回答“业务事实是什么”，Skills 约束“客服应该怎么处理、怎么措辞、什么时候升级、什么不能做”。

当前内置三类 Skills：

| Skill | 文件 | 适用 Agent | 作用 |
|-------|------|------------|------|
| 通用客服接待规范 | `skills/general_customer_service/SKILL.md` | `general` | 首轮接待、信息澄清、分流、投诉和转人工 |
| 技术支持处理规范 | `skills/technical_support/SKILL.md` | `technical` | 故障排查、接口错误、部署配置、安全边界 |
| 账单退款处理规范 | `skills/billing_support/SKILL.md` | `billing` | 扣款、退款、发票、订阅、财务审核 |

查看加载结果：

```bash
curl http://localhost:8000/skills
```

修改 Skill 文件后热加载：

```bash
curl -X POST http://localhost:8000/skills/reload
```

`SKILL.md` 推荐格式：

```markdown
---
name: 技术支持处理规范
description: 适用于 TechnicalAgent 的故障排查和升级处理规范
keywords: 报错,错误,接口,API,部署,超时,500,401,日志
agents: technical
enabled: true
---

# 技术支持处理规范

## 角色定位

...
```

字段说明：

| 字段 | 作用 |
|------|------|
| `name` | Skill 展示名称，会进入模型 prompt |
| `description` | 简短说明，便于 `/skills` 排查 |
| `keywords` | 用户消息命中关键词后才注入 |
| `agents` | 限定适用 Agent，例如 `general`、`technical`、`billing` |
| `enabled` | 是否启用该 Skill |

### 5.4 `/chat`

用途：主对话接口。

请求体：

```json
{
  "message": "我要退款",
  "user_id": "user_001",
  "conv_id": "session_001"
}
```

字段说明：

| 字段 | 必填 | 说明 |
|------|------|------|
| `message` | 是 | 用户输入 |
| `user_id` | 否 | 用户 ID，默认 `anonymous` |
| `conv_id` | 否 | 会话 ID，不传则自动生成 |

返回字段：

| 字段 | 说明 |
|------|------|
| `conv_id` | 会话 ID |
| `request_id` | 本次请求 ID，用于 `/trace/tool/{request_id}` |
| `response` | Agent 回复 |
| `intent` | 细粒度意图识别结果，例如 `refund`、`logistics`、`technical_login` |
| `intent_group` | 归一化意图组，例如 `billing`、`query`、`technical`、`escalation` |
| `agent_type` | 主返回 Agent，通常等同于主处理 Agent |
| `agent_types` | 实际参与执行的 Agent 列表 |
| `primary_agent` | 主处理 Agent |
| `supporting_agents` | 辅助 Agent 列表，复合问题时用于补充专业意见 |
| `tools_used` | 本次成功进入工具 handler 的工具名摘要；详细调用见轨迹接口 |
| `routing_reason` | 路由原因，包含意图、意图组、主辅 Agent 和领域分数 |
| `routing_confidence` | 主 Agent 路由分数 |
| `escalated` | 是否触发升级 |
| `latency_ms` | 端到端耗时 |
| `knowledge_used` | 本次是否调用过 `search_knowledge_base`；不保证查到有效文档或被回复引用 |
| `entities` | 本地规则提取的结构化实体，例如订单号、金额、错误码 |
| `intent_confidence` | 融合后的意图置信度 |
| `intent_source_scores` | LLM、Embedding、Pattern 等来源分数 |

`/chat` 不按意图预先查询知识库。普通 Agent 收到 `search_knowledge_base` 工具定义后，由模型决定是否调用；工具的查询改写、并行召回和重排只在实际调用时发生。`escalation` 节点当前直接生成交接文字，未真正创建工单。

### 5.11 工具调用轨迹 `/trace/tools` 与 `/trace/tool/{request_id}`

先发送一次 `/chat` 并记下响应里的 `request_id`，再查询：

```bash
curl "http://localhost:8000/trace/tools?limit=20"
curl "http://localhost:8000/trace/tool/替换为实际request_id"
```

单次查询返回 `request_id`、`found` 和 `trace`。`trace` 中的 `tool_calls` 逐次记录 Agent 类型、工具名、输入、调用 ID、耗时、`success`、`result_success`、`cached`、`reranked` 与错误文字；`tools_used` 只是工具名列表。没有工具调用的请求也会留下空 `tool_calls` 记录。轨迹保存在当前应用进程内存中，默认最多 200 条，进程重启或换到另一个进程后不能保证查到。

**判断 RAG 时注意**：`knowledge_used=true` 只代表 Agent 调用过 `search_knowledge_base`。MCP 的知识库 fallback 可能把降级说明包装为成功结果，而当前请求轨迹不保存结果内容或 fallback 标记。不能只看 `result_success=true` 就断定查到了真实文档。

## 6. 使用项目

### 6.1 主对话接口

请求：

```bash
curl -X POST http://localhost:8000/chat \
  -H "Content-Type: application/json" \
  -d '{
    "message": "我的订单什么时候到？",
    "user_id": "user_001",
    "conv_id": "session_001"
  }'
```

以下是字段结构示意，意图、分数、回复和工具调用随模型结果变化：

```json
{
  "conv_id": "session_001",
  "request_id": "示例请求ID",
  "response": "请提供订单号，便于进一步核实物流状态；目前我无法直接读取订单后台。",
  "intent": "logistics",
  "intent_group": "query",
```

### 6.7 意图融合、澄清和升级怎么判断

```text
LLM / Embedding / Pattern 各给出一个意图和置信度
  -> 正常权重分别为 0.7 / 0.2 / 0.1
  -> 先把同领域粗细意图分数合并，如 technical + technical_login
  -> 选最高分领域，再选领域内最高分意图
  -> Pattern 只能在同一 intent_group 内把粗意图细化
  -> 组分数低于默认阈值 0.5：返回 other
  -> other 且置信度 < 0.5、消息长度 > 2：不调用 Agent，先追问
  -> CRITICAL 或 escalation / human_handoff：走 EscalationAgent
```

例如 LLM 判为 `billing`，Pattern 判为 `technical_login`，Pattern 不会跨领域把账单意图改成登录故障。若 `technical` 与 `technical_login` 分别获得分数，它们先合并为技术组分数再与账单组比较。`intent_confidence` 是识别置信度；`routing_confidence` 是主 Agent 领域分数，两者含义不同。`escalated=true` 表示系统返回人工升级交接文字或其他升级标记，当前没有实际工单号。更完整的规则和阈值计算见 [业务流程说明](业务流程说明.md)。

### 7.4 检索知识库

```bash
curl -X POST "http://localhost:8000/search?query=退款需要多久到账&top_k=3"
```

响应示例：

```json
{
  "query": "退款需要多久到账",
  "results": [
    {
      "title": "退款政策",
      "content": "审核通过后，款项将在 5-7 个工作日内退回原支付账户。",
      "score": 0.82,
      "chunk": 0
    }
  ],
  "reranked": true
}
```

`/search` 使用的是完整检索优化链路：

```text
直接调用 POST /search，或 Agent 主动调用 search_knowledge_base
  -> 保留原始查询，LLM 尝试改写为多个子查询
  -> 每个子查询并行调用 knowledge_search（可命中 300 秒缓存）
  -> ChromaDB 召回片段，合并并按内容去重
  -> 结果多于 top_k 时尝试 LLM 重排，失败则保留原顺序
  -> 返回 Top-K；Agent 工具调用场景下再把结果交回模型
```

`/chat` 并不根据意图自动执行这条链路。只有模型实际发起 `search_knowledge_base` 工具调用，才会进入上述 RAG 步骤。知识库异常时 MCP 工具可能返回带 `fallback=true` 的“知识库降级结果”；此时 `/chat` 的 `knowledge_used` 仍可能为 `true`。导入后接口没有主动清空 300 秒检索缓存，相同 query 短时间内可能读到旧缓存。

## 8. ChromaDB 在项目中的用途

EchoMind 使用了三个 ChromaDB collection：

| Collection | 模块 | 作用 |
|------------|------|------|
| `knowledge_base` | `mcp/knowledge_base.py` | RAG 知识库文档片段 |
| `episodic` | `memory/conversation_memory.py` | 压缩后的历史对话摘要 |
| `user_profile` | `memory/conversation_memory.py` | 用户画像，包含偏好和关键实体 |

数据写入时机：

| 数据 | 写入时机 |
|------|----------|
| `knowledge_base` | 启动时自动导入默认文档，或调用 `/knowledge/add`、`/knowledge/upload` |
| `episodic` | 当前会话工作记忆超过阈值后自动压缩并写入 |
| `user_profile` | 每次 `/chat` 回复后异步提炼并更新 |

## 11. 查看工作记忆压缩内容

工作记忆压缩发生在 `memory/conversation_memory.py` 中。默认配置：

```text
WORKING_MAX = 20
COMPRESS_AT = 15
```

当同一个 `user_id + conv_id` 的工作记忆达到 **15 条消息** 时，系统会在该条消息写入过程中同步压缩。`/chat` 每轮通常写用户和助手各一条，所以不是 15 轮才触发；从空会话开始，第 8 轮写入用户消息时就可能达到第 15 条。`WORKING_MAX=20` 是单次读取上限，不是压缩触发值。

```text
旧消息 -> LLM 摘要 -> Redis summary
旧消息摘要 -> ChromaDB episodic
最近 5 条消息 -> 继续保留在 Redis wm 列表
```

日志示例：

```text
工作记忆压缩完成: cli_user/5a076f2b-b607-4339-9e9f-f0399862d366，摘要 19 字
```

其中：

```text
user_id = cli_user
conv_id = 5a076f2b-b607-4339-9e9f-f0399862d366
```


### 11.5 Redis summary 和 ChromaDB episodic 的区别

| 位置 | 保存内容 | 用途 |
|------|----------|------|
| Redis `summary:{user_id}:{conv_id}` | 当前会话压缩摘要 | 下一次同会话请求直接拼入 prompt |
| ChromaDB `episodic` | 压缩摘要 + metadata | 跨会话按语义检索相关历史 |
| Redis `wm:{user_id}:{conv_id}` | 最近 5 条消息 | 保持当前对话连贯性 |

## 12. Monitor 在线监控

查看监控摘要：

```bash
curl http://localhost:8000/monitor
```

响应包含：

```json
{
  "agent_stats": {
    "general_0": {
      "total": 10,
      "success_rate": 1.0,
      "avg_ms": 1200.3,
      "monitor_penalty": 0.0,
      "routing_score": 0.836
    }
  },
  "tool_stats": {
    "knowledge_search": {
      "total": 5,
      "success_rate": 1.0,
      "avg_latency_ms": 80.2,
      "consecutive_fails": 0,
      "circuit_state": "closed"
    }
  },
  "active_alerts": [],
  "suggestions": []
}
```

指标含义：

| 指标 | 含义 |
|------|------|
| `total` | 调用次数 |
| `success_rate` | 成功率 |
| `avg_ms` / `avg_latency_ms` | 平均延迟 |
| `routing_score` | Agent 路由评分 |
| `monitor_penalty` | Monitor 根据在线表现写回的降权系数 |
| `consecutive_fails` | 工具连续失败次数 |
| `circuit_state` | 工具熔断器状态，可能是 `closed`、`open`、`half_open` |

Monitor 默认每 10 秒采样。成功率低于 `0.90` 或平均耗时超过 3000 ms 时，对 Agent 计算并写回 `monitor_penalty`。同类有多个实例时，惩罚值进入实例的 `routing_score`；专业类型的**所有**实例惩罚值都达到 `ECHOMIND_MONITOR_FALLBACK_PENALTY`（默认 `0.5`）时，路由会把该类型排除，本次请求可能回到 GeneralAgent。可查看 `/chat` 的 `routing_reason` 是否带 `monitor_fallback=[...]`，判断这次是否真的触发了回退。告警和降级不是同一件事。

Prometheus 页面：

```text
http://localhost:9090
```

## 13. 运行端到端评测

```bash
curl -X POST http://localhost:8000/eval/run
```

评测内容：

1. 意图识别准确率和 Macro-F1
2. 调用 Orchestrator 生成真实回复
3. LLM-as-Judge 从相关性、准确性、完整性、有用性打分
4. 与上一次评测或已保存 baseline 做回归检测；指标相对下降超过 5% 才列出
5. 生成优化建议

内置意图评测用例已经使用细粒度业务意图，例如 `logistics`、`refund`、`invoice`、`payment_issue`、`technical_login`、`technical_crash` 和 `human_handoff`。

也可以提交自定义用例：

```bash
curl -X POST http://localhost:8000/eval/run \
  -H "Content-Type: application/json" \
  -d '{
    "dialog_cases": [
      {
        "turns": [
          "你好，我想退款",
          "订单号是 #12345",
          "退款多久能到账？"
        ]
      }
    ]
  }'
```

响应示例：

```json
{
  "pass_rate": 1.0,
  "total": 1,
  "passed": 1,
  "avg_scores": {
    "intent_accuracy": 1.0
  },
  "regressions": [],
  "recommendations": ["所有指标均达标，继续保持"],
  "results": [
    {
      "test_id": "intent_recognition",
      "passed": true,
      "scores": {"accuracy": 1.0, "macro_f1": 1.0},
      "detail": "准确率 100.0%，Macro-F1 1.000",
      "metadata": {
        "total": 1,
        "correct": 1,
        "cases": [{"message": "你好", "expected": "greeting", "predicted": "greeting", "confidence": 0.8, "reasoning": "问候"}]
      }
    }
  ]
}
```

上述 JSON 仅展示**只传 1 条意图用例且显式传 `dialog_cases: []`**时的字段结构，实际分数和 `cases` 会随评测结果变化。只调用空 body 时，接口会使用内置意图和对话用例，结果项数量更多。评测对话由 Evaluator 在本地维护短历史并直接调用 Orchestrator，不经过 `/chat` 的 Redis 记忆读取和画像更新；它也可能使用已注册的 Agent 工具。

## 15. 常见问题

### 15.1 `/health` 返回 503

查看应用日志：

```bash
docker compose logs -f echomind
```

重点检查：

- `.env` 是否配置 `ANTHROPIC_API_KEY`
- Redis 是否健康
- ChromaDB 是否健康
- 应用容器是否正在反复重启

### 15.2 ChromaDB 连接失败

查看 ChromaDB 状态：

```bash
docker compose ps chromadb
docker compose logs -f chromadb
curl http://localhost:8001/api/v1/heartbeat
```

应用容器内测试：

```bash
docker exec -it echomind-app bash
python - <<'PY'
import chromadb
client = chromadb.HttpClient(host="chromadb", port=8000)
print(client.heartbeat())
PY
```

### 15.3 Redis 认证失败

确认 `.env` 和 `docker-compose.yml` 中使用的密码一致。默认密码是：

```text
echomind123
```

测试连接：

```bash
docker exec -it echomind-redis redis-cli -a echomind123 ping
```

### 15.4 `/search` 没有结果

先确认知识库中有数据：

```bash
curl http://localhost:8000/knowledge/stats
```

如果是 0，可以重新导入演示文档：

```bash
curl -X POST http://localhost:8000/knowledge/upload \
  -F "file=@data/demo_docs/sample_knowledge.json"
```

再测试：

```bash
curl -X POST "http://localhost:8000/search?query=API如何接入&top_k=3"
```

### 15.5 用户画像查不到

用户画像是异步更新的，并且依赖 LLM 调用成功。排查步骤：

1. 先调用 `/chat`，使用固定 `user_id`
2. 等待几秒
3. 查看 `docker compose logs -f echomind` 是否出现 `用户画像已更新`
4. 使用第 9.6 节的 Python 脚本查询 `user_profile`

### 15.6 情景记忆查不到

情景记忆不是每次对话都写入。只有当前会话消息数达到压缩阈值后才写入。默认阈值：

```text
MemoryManager.COMPRESS_AT = 15
```

连续发 16 条以上消息后再查看 `episodic`。
